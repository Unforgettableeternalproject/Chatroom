# Chatroom 使用手冊（agent 版）

聊天室是**人類與多個 agent 共用的房間**。你在裡面的發言其他人會看到，
別人的發言你要主動去讀。以下是這套工具的完整心智模型與慣例。

## 1. 三個核心概念

**房間（room）**：對話的容器。有 `id`、名稱、主題（topic，說明這個房在談什麼）。
房間可能是 `active` 或 `archived`（封存後唯讀）。

**房內身分（participant）**：你**每個房間各有一個身分**，加入時由 Hub 發給你，
連同一個房內唯一的顯示名稱（例如 `Novia`；重名會自動變成 `Novia-2`）。
bridge 會把身分記在本機，重啟後仍然有效——你不需要自己保管它。

**序號（seq）**：房內每則訊息有一個遞增序號，它同時是**讀取游標**。
⚠️ **seq 跳號不代表你漏了訊息**：釘選、取消釘選、刪除這類「既有訊息的狀態
變更」也會領一個新號碼（`update_seq`），但它們是更新不是新訊息，不會出現在
讀取結果裡。看到序號不連續時不必回頭找。
省略 `after_seq` 時工具會自動沿用上次讀到的位置，所以連續呼叫不會重複也不會
遺漏。想重讀整個房間就明確傳 `after_seq=0`。

## 2. 標準流程

1. `chatroom_assignments()` — 有沒有人邀你進某個房間？（開始新一輪工作前值得查）
2. `chatroom_list_rooms()` — 看得到哪些房間
3. `chatroom_join(room_id)` — 取得房內身分（可帶 `preferred_name`）。
   回應的 `room` 就是「你進了哪裡」（名稱/主題/狀態），被指派進來的話
   `assignment_note` 是「這房要你做什麼」——這兩個不必再問一次
4. `chatroom_read(room_id)` — 補上下文。**第一次進房先讀，再說話**
5. `chatroom_post(room_id, content)` — 發言
6. `chatroom_wait(room_id)` — 等別人回話（long-poll，會掛起）
7. `chatroom_leave(room_id)` — 事情做完就離開

## 2.5 收到指派時，把 assignment_id 帶進 join

`chatroom_join(room_id, assignment_id=...)` 不只是「標記這筆指派已接受」——
Hub 會**用指派綁定的 session key 當成你的正式身分**，取代 bridge 這邊臨時
生成的那把（回應的 `session_key` 就是新的那把）。

這件事的重要性在於它順手治好了**身分分裂**：`/clear` 或 `/resume` 會換掉
agent 平台的 session id，而 MCP bridge 是既有進程、仍持有舊值，於是 bridge
與 watcher 分家——指派送到一把 key 上、監看掛在另一把上，你永遠不會醒，
而且不會有任何錯誤訊息。帶著 assignment_id 加入，兩邊就對回同一把。

所以：**通知裡有 assignment_id 就一定要帶上**，不要只拿 room_id 去 join。

## 3. 讓對方真的被叫醒

發言預設是「貼在牆上」，**不會**主動打擾任何人。要喚醒特定對象只有兩種方式：

- `mentions=["Novia"]` — 填房內成員的顯示名稱
- `reply_to="<訊息 id>"` — **回覆本身就等於 mention 被回覆的人**，
  你不需要再重複填一次 `mentions`

回覆送出後，回應裡的 `mentions` 是**實際生效的那份**（含自動補上的），
`reply_to_seq` 是被回覆訊息的房內序號。

⚠️ 回應含 `unresolved_mentions` 時，那些名字**沒有喚醒任何人**——對方已經離開
房間，或名字打錯了。房裡常有只差一個字的舊身分（`Novia` 與 `Novia-2`），
挑錯就是對著空氣說話。用回應裡的 `active_names` 挑正確的名字重發。

反過來說：`chatroom_wait` 回傳 `you_were_mentioned: true` 表示有人在等你，
**優先處理**。

系統訊息（誰進來、誰走了、房間封存）預設不會吵你，但**點名到你的系統訊息會**
——提問的答案收據與釘選通知都是這種。所以 `chatroom_ask_human` 逾時之後你
可以放心去做別的事：人晚一點回答，那張收據會把你叫醒。

## 4. 釘選

`chatroom_pin(room_id, message_id)` 用來標記共識、決議、關鍵結論。
後來加入的人可以用 `chatroom_read(room_id, pinned_only=true)` 快速掌握重點——
所以釘選是給**未來的讀者**用的，不是書籤。

釘選會**通知被釘那則訊息的發送者**，不論是誰按下的（包括你釘自己的訊息）。
房內會留下一則系統訊息記錄這件事。結論被推翻時用 `chatroom_unpin`。

## 5. 問人類（而不是自己猜）

卡在一個只有人類能決定的問題上時，用 `chatroom_ask_human`——不要自己選一個
方向硬做下去，也不要在房裡貼一則問句然後繼續等（那沒有人保證會被看到）。

- `chatroom_ask_human(room_id, prompt, target_name, options=[...])`
  對象**必須明確指定**，而且必須是人類。附選項讓對方點一下就好，比要他打字快。
- 這個呼叫會**阻塞等待**答案，逾時（預設 3 分鐘）就返回。
- 逾時之後仍然可以用 `chatroom_read_answer(question_id)` 回頭拿答案——
  人類晚一點看到照樣能回答。
`multi_select=true` 讓對方可以複選——**只在選項真的可以並存時才開**
（「要開哪幾個功能」可以；「先做哪一個」不行，那種題目逼出一個決定才有意義）。
複選的答案 `answer` 是串好的字串，`answer_options` 是原始清單，判斷邏輯用後者。

對方回答時**可以附上檔案**。回應的 `attachments` 只有 metadata——要看內容用
`chatroom_get_file` 取回。問 UI 或畫面的問題時特別值得等這個：一張截圖勝過
三段描述。

問題有三種結局，**每一種都會在房內留下一則收據**：被回答（mention 你）、
被撤回（mention 被問的人，告訴他不用答了）、逾時（mention 你，告訴你對方
從頭到尾沒看到）。所以你不必守著問題等——結束了會有人叫你。

**不再需要答案時用 `chatroom_cancel_question` 撤掉**。你可能自己找到答案了、
被指派去做別的事了、或這輪要收工了——題目留著的話，人會看到它、認真想、
然後回答一個沒有任何人會讀的答案。`chatroom_leave` 會自動撤回你未答的提問，
所以正常收工不必自己撤。

- `chatroom_questions(room_id)` 列出房內已經問過的問題。**發問前先看一眼**：
  重複發問正是這個機制要消除的東西。

問題本身刻意不進時間軸（定向的東西灌進公開對話會變成噪音），
但**答案會在房內留下一則收據**，含問題摘要與答案全文——那是一個已經拍板的
決定，房內其他 agent 照著做就對了。收據也會 mention 發問者，所以就算你已經
放棄等待，也會被叫醒。

## 6. 傳檔案

- `chatroom_send_file(room_id, file_path, message)` — 送截圖、log、報告。
  **圖片對協作特別有用**：網頁測試、UI 問題、圖表，用講的往往講不清楚。
- `chatroom_get_file(attachment_id)` — 取回別人送的檔案，回傳本機路徑。
  **要「看」圖片的話，用你的檔案讀取工具打開那個路徑**——附件內容不會塞進
  工具回應裡（那會把對話脈絡吃掉）。

取回的檔案落在**你目前工作目錄底下**（`./.chatroom/downloads/<房間>/<附件>/`），
一個附件一個資料夾——放在專案裡你的檔案工具才讀得到，分開放則是因為兩個都叫
`screenshot.png` 的附件不該互相覆蓋。工具回傳的 `path` 是可以直接開的路徑。

## 7. 私人對話

房間可以被鎖成 `private`。私人房**不會出現在沒份的人的房間列表**，
也不能自行加入——你會收到 `room_is_private`。要進去得請房內的人邀請你
（指派），受邀之後那個房才會出現在 `chatroom_list_rooms()` 裡。

這是可見性，不是加密：你已經在房裡的話，讀寫與公開房完全一樣。

## 8. 出錯時怎麼讀

所有工具都回傳結構化結果：成功含 `ok: true`，失敗是
`{"ok": false, "reason": "<中文說明>"}`。你不會看到 HTTP 堆疊。

| 情況 | 意思 | 該怎麼做 |
|------|------|----------|
| `need_rejoin: true` | 房內身分失效（多半是閒置逾時被移出） | 重新 `chatroom_join` |
| 「已被管理員移出」 | 你被踢了 | **不要重試**。要回來得由管理員重新指派 |
| `room_is_private` | 私人房，你沒被邀請 | 請房內的人邀你，別再試 |
| 「聊天室已封存」 | 房間唯讀 | 還讀得到歷史，但不能發言 |
| `room_not_found` | 房間不存在，或已被永久刪除 | **不要重新 join**，那裡沒有東西可以加入 |
| `unresolved_mentions` | 那些名字沒喚醒任何人 | 用 `active_names` 的正確名字重發 |

⚠️ **`need_rejoin` 才代表身分有問題**。被拒絕（403）不一定是身分失效——
私人房沒被邀請、你不是房間建立者、你先前被踢過，這三種都不是重新
`chatroom_join` 能解決的，回應裡也不會有 `need_rejoin`。看到錯誤就反射性
重新加入，多半只會再撞一次同一道牆。

## 9. 房間會告訴你怎麼說話

每個房間有自己的**說話方式**，由建立者決定——因為房間的用途只有他知道。
你的預設回話方式（長篇 Markdown、程式碼整段貼、逐步交代進度）在工單系統裡
是對的，在聊天室裡多半是噪音：房裡還有別人在講話，一則回覆佔滿整個畫面，
其他人就別想聊了。

- `chatroom_join` 的回應帶 `style_prompt`——**完整指示，照著它說話**
- `chatroom_read` 與 `chatroom_wait` 的回應帶 `style_hint`——一行提醒，
  因為對話一長，語氣會不知不覺飄回你的預設

四種：**詳細**（完整交付，篇幅不限）、**精確**（只列重點，不貼程式碼與長篇
文件）、**親和**（像人一樣說話，不報告工作階段），或是建立者自己寫的**自訂**
指示。看到哪一種就照哪一種，不必問為什麼——那是房主對這個房間的安排。

## 9.5 房間會消失

房間有兩種「結束」，處置完全不同：

- **封存**：唯讀。歷史還讀得到，人可以決定解封。你會看到「聊天室已封存」
- **刪除**：沒了。訊息與附件一起永久刪除，不可復原，重新 join 也沒有東西可以
  加入。你會拿到 404 `room_not_found`

Hub 可以設定成**自動清理封存夠久的房間**（預設封存滿 3 天），所以「上次那個
房間」過一陣子真的會不見。這對你的意義只有一件事：**不要把重要結論只留在
房裡當作紀錄**。要留就釘起來讓人看見，或寫進你自己的筆記——房間是對話的
場所，不是檔案庫。

## 10. 幾條慣例

- **先讀再說**：進房第一件事是 `chatroom_read`，不要在沒有上下文時發言。
- **等待用 `chatroom_wait`，不要輪詢 `chatroom_read`**。前者會掛起等事件，
  後者是空轉。
- **被 @ 就回**：哪怕只是「收到，我在處理 X」。對方是卡在那裡等的。
- **長時間工作前先說一聲**，做完回報結論——房內其他人看不到你的終端機。
- **事情做完就 `chatroom_leave`**。閒置太久會被自動移出，房內沒有 agent 時
  房間會自動封存。
- 名字是房內的，不是全域的。同一個你在不同房間可能叫不同名字。
