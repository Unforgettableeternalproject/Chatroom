# Chatroom v1.2.2

Multi-Agent 聊天室通訊層的第一個正式版本。

讓正在工作的 agent（Claude Code、Codex）與人類加入同一個聊天室協作：讀訊息、發言、
釘選決議、指派工作、共用任務板。只做通訊架構，不做沙盒、不包裝 agent。

這是 `master` 分支的首次正式釋出，累積超過 670 顆 commit。

---

## 三端架構

### Hub（server/）

FastAPI + SQLite，整個系統的唯一真相來源。

- **聊天室與成員**：房間建立、加入、退出、永久刪除。名稱在「房內 active 成員」層級
  唯一，由 partial unique index 保證。
- **訊息**：以房內遞增 `seq` 作為 cursor，通知與分頁共用同一個游標，保證不重複也不遺漏。
  支援回覆、釘選、軟刪除、編輯、附件。
- **提及與指涉**：`@成員` 會喚醒對方；`#[卡片標題]` 指向任務板上的卡。兩者都要求
  「欄位與內文一致」，避免出現指了卡卻點不下去的訊息。
- **任務板**：三層結構 Objective（週期）→ Checklist（階段）→ Task（任務）。含認領、
  指派、狀態轉移、送審與確認閘、監督者、週期收尾。
- **想法板**：段落層級的共筆，每段記錄作者與版本號。人類寫的段落 agent 不能改寫，
  只能在旁邊掛註解。
- **向人類提問**：agent 可指定房內某個人類提問並等待回答，答案在房內留下收據，
  其他 agent 看得到同一個決定，不必重複問。
- **指派**：把 agent session 指派進特定房間，對方加入時自動標記為已接受。
- **私人房**：不出現在沒份的人的對話列表，未受邀不能加入。這是可見性而非安全邊界，
  token 才是這個系統的信任邊界。
- **說話方式**：房間可設定 agent 的回話風格（詳細／精確／親和／自訂），指示由 Hub
  送到 agent 眼前，避免長對話中語氣飄回預設。
- **生命週期**：presence sweeper 定期清理閒置成員，房內無 active agent 時自動封存；
  封存房唯讀，預設保留 3 天後清理，啟動時會先把待刪名單列進日誌並延後第一輪。
- **推送**：WebSocket 給介面，long-poll 給 agent，共用同一套增量機制。

### MCP Bridge（bridge/）

獨立安裝的 Python 套件，把 Hub 的 REST API 包成 MCP 工具，讓 Claude Code 與 Codex
直接在對話中使用。刻意做成薄殼，業務邏輯全部留在 Hub。

- 安裝後產生 `chatroom-mcp`（stdio MCP server），可裝進專案 venv 或任何乾淨的 venv。
- 內建使用手冊（`chatroom_guide`），與 `docs/CHATROOM.md` 逐字同步，由測試釘住不許漂移。
- 附常駐 watcher：被提及或收到指派時喚醒 agent，沒被提及的訊息靠游標補讀，不打擾。
- 安裝器在動任何檔案之前先檢查 agent 端能力，缺少必要條件直接中止而非留下半成品。

### 桌面 App（app/）

Flutter 的 Windows 桌面介面，人類這一端。

- 聊天室、任務板、想法板、板庫的完整介面。
- 訊息串支援釘選牆、跳轉、卡片指涉、提及高亮、附件預覽。
- Host Console：啟動與停止 Hub、開關對外隧道、備份與還原、token 輪替、開機自啟。
- 指派介面：掃描本機的 agent session 並派工。

## 這一輪的修復（2026-09-14 至 09-15，24 顆）

### 用語一致性

同一個東西在不同地方叫不同名字，是這一輪修掉的最大一類。三個層級的中文說法全部收斂，
英文識別字一律不動。

- Checklist 那層在人看的字串裡一律叫「階段」。先前同時存在「階段」「清單」「階段清單」
  「階段分組」四種叫法，連「同一份東西建立時叫階段、刪除摘要叫清單」都有。
- 聊天室不再一下叫「房間」一下叫「聊天室」，任務板不再一下叫「板子」。修正前有句子
  在同一句話裡就用了兩種叫法。
- App 端的搬移流程把「階段」叫成「清單」，同一層在兩處兩個名字。

用語的射程刻意劃在「同一句、同一語境裡對同一個東西換名字」，不是把某個詞從詞彙表除名。
動賓搭配（封存房間）、指代（這間房）、診斷日誌不在範圍內。

### 訊息與任務板的連動

- 從訊息點卡片會離開聊天室，而且落在別的週期。
- 房間換過板之後，舊訊息上的卡片指涉點了沒反應。
- 本房沒掛板時，卡片指涉仍被誤判成「同一塊板」。
- 卡片指涉與成員提及同色，一排看過去分不出點下去會跳到哪。

### 通知與回饋

- 指定任務板監督者時，通知要叫得醒被指定的那個人。先前房內留了痕跡，當事人卻不會收到。
- 送出訊息前看得到「這則會 tag 到誰」，打錯名字當場就看得出來。
- 啟動 Hub 與開啟隧道要有進行中狀態與結果。先前兩個「停止」操作都有回饋，兩個「啟動」
  沒有，按了不知道成功與否。
- 回饋機制本身的四個缺陷：進行中狀態卡死、跨區覆寫、按鈕復活、假成功。
- 已經有一條隧道時封掉「再開一條」，那會留下一條關不掉的公開入口。
- 禁用的按鈕要真的禁用，不是點了沒反應。

### 產品識別

- 視窗標題與產品名稱先前還是 Flutter 骨架留下的 `chatroom_app`，已改為 `Chatroom`。
- 換上正式 logo（app icon 與介面左上角標示），並補上先前缺少的 20 與 40 DPI 尺寸。
- 執行檔更名為 `Chatroom.exe`。

其中一顆修復值得單獨說明：更名產品識別會改變 Windows 上設定與憑證的存放路徑，等於把
所有既有使用者的設定與登入狀態搬走。該問題在釋出前被攔下並修正，升級不會遺失設定。

### 文件

- 記錄「在 `.claude/worktrees/` 底下 build Windows 專案會超出 MAX_PATH」，差一個字元。
  該錯誤的訊息形式像權限問題，而系統層的長路徑支援對 MSBuild 的 FileTracker 無效，
  兩個特徵都會誤導追查方向。

## 升級與安裝

- **App**：`Chatroom.exe`。設定與憑證沿用既有路徑，升級不需要重新輸入伺服器位址或 token。
- **MCP kit**：Windows 上原地升級前需先停止持有執行檔的 MCP 進程，否則 pip 會因檔案
  被占用而失敗。安裝器在失敗時會保留可用的舊版本，不留下半毀的環境。
- **Hub**：程式碼更新後需要重新啟動行程才會生效。版本資訊在啟動時凍結，
  `/api/health` 回報的 commit 即為該行程實際載入的版本。
