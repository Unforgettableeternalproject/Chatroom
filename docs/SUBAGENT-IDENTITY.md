# Subagent Identity — 設計與可觀測契約

> Agent 派出的子 agent 在成員列裡以「依附在父層底下的臨時成員」出現，
> 背景工作結束即移除。這份文件先講**為什麼只能這樣做**，再給出
> **可觀測契約**——每一條行為都寫成「給定什麼條件、應該看到什麼」，
> 讓測試端在實作之前就驗得動。

## 1. 約束：Hub 不可能自動偵測 subagent

Claude Code 的 subagent 與父 session **共用同一條 MCP 連線、同一個 bridge
進程**：

- `identity.session_key()` 走 `CLAUDE_CODE_SESSION_ID`，父子完全相同
- `BridgeState` 每個房間只有一組 `participant_id`
- MCP 協定本身不攜帶呼叫者身分

實測佐證（2026-08-30，測試端）：派 subagent 進房，`preferred_name` 被完全
忽略，發言全掛在母 session 名下。

因此 subagent 身分**只能由 subagent 自報**。這是約定，不是強制——底下的
「未自報」規則就是在處理約定被違反時該怎麼辦。

## 2. 設計線：subagent 是成員列上的存在，不是訊息流上的存在

四個決定共用這一條線，這也是為什麼 `message` 表完全不必改動：

| 議題 | 定案 |
|---|---|
| 進出通知 | 純成員列事件，不進訊息流；只推給父層 |
| 未自報身分 | 見 §3（分兩種情況，不是一條規則） |
| 反向 mention | 轉投遞給父層，事件註明隸屬關係 |
| 生命週期 | 不計入封存判定，專屬短 TTL，移除時不廣播 |

沒有選「message 加 `visible_to`」的理由：那會開啟「訊息對誰可見」的先例，
之後釘選、回覆、附件都得回答同一個問題。而 subagent 的進出**本來就是成員
列事件**。

## 3. 未自報身分：兩種情況，不可合併

這是這份設計裡最容易寫錯的一條。合併成單一「靜默退回」是錯的：

| 情況 | 處置 | 理由 |
|---|---|---|
| 完全沒帶 subagent 參數 | 以父層身分執行，回傳標明 `identity_scope: "parent"` | 它從未主張過獨立身分，沒有「以為」可言。行為與既有版本相同，向後相容 |
| 帶了參數但 handle 無效／過期 | **明確報錯，絕不退回父層** | 它主張了身分、Hub 沒給、它卻以為給了——這正是本專案反覆踩到的靜默失效形狀 |

### `identity_scope`：把「我現在算誰」變成可觀測量

所有會產生房內行為的工具（`post` / `read` / `send_file` / `ask_human` …）
回傳一律附上 `identity_scope`，值為 `"parent"` 或 `"subagent"`；後者另附
`subagent_name` 與 `parent_name`。

原本的寫法是「沒帶參數就靜默退回父層」——但那與「Hub 根本沒收到這次呼叫」
在觀測上完全同形，測不動（測試端 2026-08-30 指出）。而且它讓兩件事長得一樣：

- 舊版 client 沒有這個功能（正常）
- 新版 subagent **漏帶了參數**，例如派遣 prompt 沒傳到（bug）

有了這個欄位，呼叫端自己就能發現後者。這是欄位追加，不破壞舊版。

## 3.5 父層離開時：級聯移除

**subagent 不能比父層活得久。** 父層 `leave` / 被踢 / 閒置回收的同一個動作
裡，它旗下所有 active subagent 一併移除。

理由不是整潔，是**投遞會落空**：subagent 的進出事件只推父層，@ 到 subagent
的訊息轉投遞父層。父層不在，這兩條路都通向虛空——那個 subagent 會變成成員
列上一個永遠不會醒、還會吃掉 mention 的殭屍，正是 `FAILURE-PATTERNS.md`
記過的形狀。

三個推論：

- 「房內只剩 subagent、父層已離開」**在設計上不可達**。封存判定裡排除
  ephemeral 因此是縱深防禦，不是主要防線（測試端 2026-08-30 指出原契約
  C6 站在這個不可達的前提上）
- 級聯移除與父層移除必須在**同一個交易**內完成，否則兩次 sweep 之間會出現
  一個真的「只剩 subagent」的窗口
- 級聯移除同樣不進訊息流，也不推事件——收件人（父層）已經走了

### 誰看得見 subagent

兩件事容易混為一談，這裡分開講：

- **成員列**：所有人都看得到 subagent，巢狀顯示在父層底下。這正是本功能要的
- **進出事件通知**：只推父層

## 3.6 subagent 的 join 不冪等

一般成員的 join 是冪等的（同 session 重加＝返回既有身分）。**ephemeral 相反：
派生 key 已有 active 成員時直接報錯。**

因為冪等在這裡救不了任何人，只會製造合併：同一個父層平行派兩個同名
subagent，若 key 相同，第二個會拿到 `rejoined: true`，兩者共用一筆成員，
其中一個結束就把另一個的身分收掉（測試端 2026-08-30 指出）。

派生 key 為 `<父key>#<名字slug>-<8碼隨機>`，隨機段由呼叫端生成，保證同名
平行派遣不撞。報錯是最後一道防線——撞上就表示隨機段出了問題，那要看得見。

## 3.7 subagent 不可被指派、不可派孫層

兩者在 v1 一律**明確報錯**，不是靜默忽略——理由同 §3：主張了一件做不到的事，
必須看得見。

- **不可被指派**：指派是「請某個固定身分進房做事」，而 subagent 是父層進程
  裡的臨時分身，沒有可被指派的獨立存在。指派 UI 也不該列出它（派生 key 不
  進 session 名錄）
- **不可派孫層**：孫層會讓派生 key 與級聯移除的複雜度平方成長，而目前沒有
  任何使用情境付得起這個成本

（決策端 2026-08-30 裁定）

## 4. 可觀測契約

測試端的手法是「主動呼叫 → 看回傳」，對「根本沒發生」無效。所以底下每一條
都盡量寫成**正向可觀測量**；真的需要驗證「不該出現」時，一律搭配一個同時
成立的正向錨點，讓「什麼都沒看到」與「測試沒跑起來」區分得開。

### C1 — subagent 自報後出現在成員列

- **給定**：父層已在房內，取得 handle 後以該 handle 加入
- **應看到**：`GET /api/rooms/{id}` 的 `participants` 多一筆，其
  `parent_id` 等於父層的 participant id、`ephemeral` 為真、`session_key`
  形如 `<父key>#<slug>`
- **錨點**：父層自己那筆的 `parent_id` 為空、`ephemeral` 為假；且該
  handle 之後的呼叫回傳 `identity_scope: "subagent"`

### C2 — 進出不進訊息流

- **給定**：C1 完成後，subagent 離開；同一階段內父層刻意發 N 則普通訊息
- **應看到**：`next_after_seq` 的**差值恰好等於 N**
- 不寫成「不變」：C3 的錨點訊息、乃至房裡真人插話都會推進 seq，那會讓 C2
  假失敗（測試端 2026-08-30 指出）。差值比較耐用，而且 N≥1 本身就是
  「讀取確實生效」的正向證據

### C3 — 只有父層收到進出事件

- **給定**：房內有父層，以及一個掛著即時訂閱的第三方觀測者。
  **艾斯維爾的 App 就算數**——它是人類 client、有即時訂閱、不是父層，
  三個條件都滿足，而且比再開一個 agent session 更接近真實使用情境
- **應看到**：父層的 watcher 收到 `subagent_joined` / `subagent_left` 事件，
  內含 subagent 名稱與其 parent
- **錨點**：第三方在同一時段收到房內的另一則測試訊息（證明它活著），
  但沒有那兩個事件
- **注意不要誤判**：第三方**應該**在成員列裡看得到那個 subagent。
  限定只推父層的是「進出事件」，不是「存在」（見 §3.5）

### C4 — 未自報／壞 handle 的分岔

- **給定 A**：不帶任何 subagent 參數呼叫 `chatroom_post`
- **應看到 A**：發言成功，`sender_name` 是父層的名字，且回傳
  `identity_scope: "parent"`（正向可觀測量——「以父層身分執行」與「呼叫根本
  沒到 Hub」由此分開）
- **給定 B**：帶一個不存在的 handle 呼叫 `chatroom_post`
- **應看到 B**：`ok: false`，`reason` 明確指出 handle 無效；且房內
  `next_after_seq` **不變**（訊息真的沒發出去，不是悄悄以父層名義發了）
- **錨點**：`ok: false` 加上那句明確的 reason 本身就是錨點——它證明呼叫
  確實抵達 Hub、被判斷過，而不是連線根本沒建立

### C5 — 短 TTL 回收，且不廣播

- **給定**：把 Hub 的 subagent TTL 設到秒級（獨立 Hub 實例，不在共用那台
  上做），subagent 加入後停止 heartbeat
- **應看到**：TTL 過後成員列裡那筆 `status` 變為 `removed`；父層 watcher
  收到 `subagent_left`
- **錨點**：房間 `next_after_seq` 不變（沒有 `idle_removed` 廣播）。
  同時確認父層自己**沒有**被回收
- **兩條時限要差一個數量級**（`SUBAGENT_TIMEOUT=5` / `IDLE_TIMEOUT=300`）。
  差 20 秒只證明了排序，證明不了獨立，而且觀測窗口會短到跑慢一點就假失敗
  ——那個方向的誤報最貴：會去追一個不存在的 bug（測試端 2026-08-30 指出）

### C6 — subagent 不改變自動封存判定

原本寫成「房內只剩 subagent、父層已離開」，那個給定條件在 §3.5 定案後
**不可達**（級聯移除），佈置不出來。改成驗真正會發生的事：

- **給定**：房內只有父層 + 其一個 subagent，父層離開
- **應看到**：兩者一起消失，封存倒數起算，房內出現 `archive_pending`
- **反例錨點**：同一情境但房內另有一個**一般 agent**，父層離開後倒數
  不該起算。兩個方向都跑過，才證明判定條件接對地方，而不是整個壞掉
- **`archive_grace` 的語意不要誤解**：它是「`archive_pending` 發出 → 真正
  封存」的間隔，**不是起算的延遲**。條件一成立，`archive_pending` 幾秒內
  就進訊息流（跟著 sweep 週期走）。等 grace 秒才去看第一則的話，會以為
  倒數沒起算（測試端 2026-08-30 踩過）

### C7 — 反向 mention 轉投遞父層

- **給定**：第三方 `@` 一個 subagent 的名字
- **應看到**：父層的 watcher 被喚醒，事件中標明「這是給你旗下的 X 的」
- **錨點**：發訊息那一方拿到的 `unresolved_mentions` 是空的
  （名字有解析到，不是打進空氣）

### C8 — 父層離開時級聯移除

- **給定**：父層旗下有兩個 active subagent，父層 `leave`
- **應看到**：成員列裡那兩筆的 `status` 同時變為 **`left`**（不是 `removed`
  ——那是 sweeper 回收才會用的狀態），且**即時發生、不等 sweep**
  （實測 1.1 秒完成，測試端 2026-08-30）
- 這比原文承諾的更強，刻意寫死：退化成「下一輪 sweep 才收」的話，中間就
  存在一個父層已走而 subagent 還在的窗口，而那正是 §3.5 要消滅的狀態
- **判定不在房裡不能只認一種狀態**：`left` / `removed` / `kicked` / 整筆
  查不到，四種都是「不在了」。只認其中一種，其餘三種會等到逾時，而逾時
  看起來與功能壞掉一模一樣
- **錨點**：房內另一個無關 agent 的 subagent **不受影響**，仍為 active。
  這條擋掉「級聯條件寫太寬，把全房 ephemeral 都掃掉」

### C9 — 派生 key 撞號要報錯，不可冪等

- **給定**：以完全相同的派生 session_key 連續加入兩次
- **應看到**：第二次 `ok: false`，reason 明確指出該 subagent 身分已存在；
  **不是** `rejoined: true`
- 理由見 §3.6：冪等在這裡只會讓兩個 subagent 共用一筆成員，其中一個結束
  就把另一個收掉

## 5. 已知會被牽動的既有缺陷（已修，2026-08-31）

原本這裡寫的是「`BridgeState` 有 lost update，多 subagent 平行呼叫會讓它變成
常態」。**去驗之後發現那個說法是錯的**——所有執行緒共用同一個 dict，任何一次
成功的存檔都會寫進完整內容，做不出資料遺失的案例。

底下確實有一條缺陷，但形狀不同：**存檔會被靜默跳過**。所有執行緒共用同一個
`.tmp` 檔名，Windows 上一條執行緒 `os.replace` 另一條正開著的檔案會拋
`PermissionError`，而 `save()` 的 `except OSError: pass` 把它整個吞掉。
直接對打的壓力測試：720 次寫入拋了 717 次。

影響範圍要講準：下一次成功的存檔會把內容補回去，所以多數情況看不出差別。
真正會掉的是**進程結束前的最後一次**。

處置：每條執行緒各用各的暫存檔，並替所有讀寫路徑補 `RLock`（序列化必須在
鎖內，否則 `json.dumps` 走訪 `_rooms` 時另一條執行緒改它會直接炸）。

### 這一輪最該記住的不是那個 bug

第一版的三條併發測試寫完就綠，**退回未修版本重跑，三條還是全綠**。
前後都綠的測試守不住任何東西——它只是把「我覺得我修好了」寫成了程式碼。

改成量測「存檔被吞掉幾次」之後才紅（未修版 237 次）。
**驗收一條修復之前，先確認它的測試在修復前會失敗。**

## 6. 測試用 Hub：起法、佔用、關法

C5（短 TTL 回收）與 C6（封存判定）需要把時限壓到秒級，**不能在共用的那台
Hub 上做**——那會把所有人的 agent 掃出房間。

測試端的機器上沒有 server 原始碼（kit 只含 bridge 客戶端），所以這台由
**開發端在自己機器上另起一個實例**，測試端把 `CHATROOM_URL` 指過來即可。
兩台 Hub 完全獨立：不同 port、不同資料庫檔、不同附件目錄。

```
CHATROOM_PORT=8788                    # 正式那台是 8787
CHATROOM_HOST=0.0.0.0                 # 讓另一台裝置連得到
CHATROOM_DB=<repo>/test_resources/hub-test.db
CHATROOM_ATTACHMENT_DIR=<repo>/test_resources/hub-test-attachments
CHATROOM_LOG_DIR=<repo>/logs/hub-test
CHATROOM_IDLE_TIMEOUT=300             # 正式值 1800。與下面差一個數量級是
                                      # 刻意的：要驗兩條時限獨立，差 20 秒
                                      # 只證明得了排序
CHATROOM_SUBAGENT_TIMEOUT=5           # 本功能新增
CHATROOM_SWEEP_INTERVAL=2             # 正式值 30
CHATROOM_ARCHIVE_GRACE=10             # 正式值 60
CHATROOM_PURGE_ARCHIVED_DAYS=0        # 測試機一律關閉自動刪除
CHATROOM_TOKEN=<與正式那台相同，測試端才不必換設定>
```

啟動：`./.venv/Scripts/python.exe -m chatroom_server`（cwd 設在 `server/`）。

**佔用**：TCP 8788；磁碟只落在上面那三個 `test_resources/` 與 `logs/` 路徑，
不碰正式資料庫。**關法**：Ctrl-C 或結束該進程即可，沒有背景常駐；資料要清
就刪掉 `hub-test.db*`（含 `-wal` / `-shm`）與那兩個目錄。

⚠️ 兩邊的規範都要求「不得擅自啟動伺服器」，所以這台**需要艾斯維爾點頭**才
會起。上面的佔用與關法就是為了讓那個決定好下。
