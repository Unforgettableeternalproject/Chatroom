# 兩個 Kit 的介面 — 設計簡報（Design Brief）

> 對象：`host-kit`（Hub 主持包）與 `install-kit`（MCP 安裝包）的介面。
>
> ⚠️ **這份不是規格，是問題清單加上主張。** 第五節每一條都是「我們知道會很難
> 但沒有標準答案」的地方，歡迎推翻。
>
> **形式：Flutter 桌面應用**（艾斯維爾裁定 2026-09-09）。視覺語彙、深色模式、
> 色票與字型 token 全部沿用 `app/lib/core/theme/`，**不要另起爐灶**——這一點
> 與 `BOARD-DESIGN-BRIEF.md` 的要求相同。
>
> 「獨立 exe」還是「併進既有 Chatroom App 當一個分頁」待裁定；資訊架構與狀態
> 模型兩案共用，那才是這份文件的主體。

## 一、這是給誰的

**一個第一次拿到 zip、想把伺服器跑起來的人。** 他不一定寫程式，多半不會讀完
README，而且他遇到問題的時候，手邊沒有我們任何一個人。

兩包的受眾不同，難度也不同：

| | host-kit | install-kit |
|---|---|---|
| 使用者 | **主持人**：架 Hub、發連線資訊、出事要修的那個人 | **成員**：只想讓自己的 agent 連上去 |
| 一次性 vs 持續 | **持續**——伺服器要一直活著，隧道要重開，token 要換 | **幾乎一次性**——裝好就不太動 |
| 出事的後果 | 所有人都連不上 | 只有他自己連不上 |
| 介面份量 | 主體 | 較輕 |

## 二、現況（可觀察的事實，不是抱怨）

兩包都是 `python install.py` 走完提示，之後靠記憶與 README 操作：

- 啟動 Hub：`scripts\run-hub.cmd`（前景）或 `hub-service.ps1 install` → `start`
- 開隧道：`scripts\run-tunnel.cmd`
- 確認活著：`curl http://<位址>:<埠>/api/health`
- 要發給成員的東西：`install.py` **結尾印一次**

**問題不在指令難記，在「現在是什麼狀態」完全不可見。**

沒有任何一個地方能回答：Hub 跑著嗎？服務註冊了嗎？隧道開著嗎、網址是什麼？
token 是什麼？成員現在連得進來嗎？

而 `install.py` 結尾印出的那份連線資訊——**那是要發給每一個成員的東西**——
關掉終端機就沒了，只能去翻 `server/.env`。

## 三、要解決的核心問題

> **把「現在是什麼狀態」與「下一步該做什麼」變成一眼的事。**

不是做一個功能齊全的管理台。主持人要的不是更多按鈕，是**看得懂現在的處境**。

## 四、資訊架構

### 4.1 host-kit：三盞燈，不是一盞

這是整份設計最重要的一塊。

現在「成員連不上」是一個症狀，但它底下是三件**彼此獨立、症狀相同、處置完全
不同**的事：

| 燈 | 問的問題 | 怎麼驗 | 壞掉時該做什麼 |
|---|---|---|---|
| **① 進程** | Hub 活著嗎 | 本機 `/api/health` | 啟動 Hub／看 log |
| **② 可達** | 從外面連得進來嗎 | 從綁定位址連一次 | 防火牆放行／確認 VPN／檢查綁定位址 |
| **③ 認證** | token 對不對 | 帶 token 打一次 | 對照 `.env` 與發出去的那份 |

README 的疑難排解段其實已經隱含這個結構（「依序確認：進程活著 → 防火牆放行 →
VPN 通」），但那是一段要讀的文字。**介面該把它變成三顆各自會亮的燈**——
主持人看一眼就知道自己在哪一關，而不是從頭試一遍。

⚠️ ② 有一個真實的陷阱，隧道腳本已經踩過並寫進註解：**從自己的機器繞回自己的
公網網址常常走不通**（路由器不支援 hairpin、本機 DNS 只解到沒有出口的那一族）。
所以 ② 的紅燈**不等於外面連不進來**。這盞燈必須講清楚它驗到的是什麼，
否則它會製造假警報，而假警報比沒有燈更糟。

### 4.2 host-kit：「發給成員的東西」是常駐區塊，不是一次性輸出

一塊永遠在畫面上、可整段複製的區域：

- Hub 位址（內網／VPN）
- 隧道網址（開著時才有，**每次重開都會變**）
- token
- 給成員的一句話說明（「把這三行貼進 install.py 的提示」）

**隧道網址每次都變、每次都要重發給所有人**——那件事在畫面上該是「複製」一個
動作，而不是從一堆輸出裡把它找出來。

### 4.3 host-kit：需要出現在畫面上的操作

| 操作 | 現況 | 備註 |
|---|---|---|
| 啟動／停止 Hub | `run-hub.cmd` | 前景與服務兩種模式的差別要看得出來 |
| 註冊／移除開機自啟 | `hub-service.ps1` | 一般權限＝登入時自啟；管理員＝開機自啟。**這個差別現在只寫在 README** |
| 開／關隧道 | `run-tunnel.cmd` | 見 §5 的警告時機 |
| 換 token | 改 `.env` 重啟 | 成本很低，但現在沒人知道 |
| 看 log | 翻 `logs\` | 出事時第一個要看的東西 |
| 備份 | `VACUUM INTO` | ⚠️ **db 與 `attachments/` 是兩份東西**，只備份 db 還原後圖全變 410 |

### 4.4 install-kit：更輕，但有一個特別的難處

成員端要回答的只有三題：**連得上嗎、我是誰、agent 認得這些工具了嗎。**

但它有一個 host-kit 沒有的問題：**它裝的東西不在自己的資料夾裡。**
它會改 `~/.claude` 的 MCP 設定與 `~/.codex/config.toml`——那是最容易出錯、
也最看不見的部分。畫面該直接顯示「我改了哪些檔案、那些檔案現在寫著什麼」。

⚠️ **今天實際踩到的一個坑值得做進介面**：測試端那把 09-07 的 bridge 沒有
`card_refs` 參數，發文被 Hub 擋下，而錯誤訊息指向 App 的 UI（她是 agent，
根本沒有那個東西）。根因是 **bridge 進程比安裝的版本舊——設定檔更新了，
但 Claude Code 沒重啟**。

介面該能講出這件事：「已安裝 x.y.z，但目前跑著的 agent 連的是舊的，請重啟
Claude Code」。這是一個安裝器天然看得見、而使用者天然看不見的落差。

## 五、值得思考的點（每一條都是問題）

- **警告要出現在它有意義的那一刻。** README 有一整段寫 token 的信任邊界寫得
  很好——「token 是信任邊界，房間不是」「持 token 的人讀得到所有房間，包含他
  沒加入的、以及已封存的」。但它在 README 第 60 行，而**不讀 README 正是這個
  介面要服務的族群**。那段話真正需要被讀到的時刻是**按下「開隧道」的當下**。
  問題是：怎麼讓它被讀進去而不變成一個被反射性關掉的對話框？

- **這個介面大部分時間是「沒事發生」。** 它跟 Board 一樣，掃視比操作重要——
  主持人多半只是想確認一切正常。所以正常狀態要能一眼掃過，異常狀態要跳出來。

- **「不確定」是一種狀態，不能畫成「壞掉」。** §4.1 的 ② 是最好的例子：
  從自己的機器測自己的公網網址失敗，多半不是隧道壞了。介面上需要第三種顏色，
  以及一句「這個檢查在這裡本來就不準，要從外部確認」。

- **失敗訊息要指向使用者能改的東西。** 這是今天在另一條線上重複咬了三次的
  教訓：同一句錯誤訊息，對三種不同的呼叫端都指向了他手上沒有的東西。
  kit 的每一句錯誤都該問一次「他看完這句話，下一個動作是什麼」。

- **不要把安裝與日常操作混成同一個畫面。** 安裝是一次性的、線性的；日常是
  持續的、隨機存取的。同一個入口做兩件事，會讓已經裝好的人每次都要繞過安裝流程。

- **這個介面自己不能變成另一個要維護的東西。** 它應該薄到「壞了也不影響 Hub」
  ——所有操作都是既有腳本的包裝，不新增第二條真相來源。

## 六、形式相關（Flutter）

### 6.0 界線：host-kit 是伺服器，App 是它的遙控器

**兩個都要，而且這個分工不該被消除。**（艾斯維爾提問、2026-09-09 房 seq 142
討論；⚠️ 待他最終裁定）

Hub 是 Python（FastAPI + aiosqlite），Flutter app 打包不進 Python 直譯器——
除非塞一份 embedded Python，那會讓 App 肥好幾十 MB，並且變成「App 帶著一個
沒有人會去更新的 Python」。所以伺服器本體必然來自 host-kit。

**但那是好事，三個理由：**

1. **App 掛掉不能影響 Hub。** 伺服器若活在 App 進程裡，關掉視窗就是斷線所有人。
2. **伺服器常常跑在沒有 GUI 的機器上**，可服務化、可 ssh 進去操作。把啟動路徑
   綁進桌面 App，那種機器就沒救了。
3. **兩邊更新節奏不同。** 介面改一次要重 build 重散布 App；Hub 改一次只換
   Python 檔。綁在一起會讓「改一顆按鈕」變成「所有人重裝伺服器」。

於是界線是：

- **host-kit 保留完整的命令列路徑**，不裝 App 也能跑（現況不動）
- **「主機」分頁是可選的控制台**，做的每件事都是既有腳本的包裝，
  不新增第二條真相來源
- **偵測機制**：host-kit 安裝時寫一份註冊檔（例如 `~/.chatroom/host-kit.json`
  記下安裝路徑），App 讀得到才顯示分頁；讀不到就當這台沒有 Hub，
  **分頁整個不存在**——見 §6.1

### 6.1 這個 app 與 Chatroom App 的根本差別

Chatroom App 是**客戶端**：它連到某台 Hub，可以在任何機器上跑。
這個介面是**主機控制台**：它管理**本機**的 Hub 進程、本機的檔案、本機的服務
註冊——**它只在 Hub 那台機器上有意義**。

這個差別會長出兩個具體後果：

- 它需要 `Process.run`（起停 Hub、開隧道、呼叫 `hub-service.ps1`）與檔案系統
  存取（讀 `server/.env`、`logs/`），而 Chatroom App 完全不需要這些
- **併進既有 App 的話，那個分頁在別台機器上必須消失**——不是變灰，是不存在。
  一個永遠按不動的分頁比沒有這個功能更糟

### 6.2 沿用什麼、不新增什麼

- 色票、字型、深色模式：`app/lib/core/theme/` 既有 token
- 狀態顏色：§4.1 的三盞燈需要「好／壞／**不確定**」三種，而既有語彙裡
  「不確定」這一種可能還沒有——**這是唯一可能需要新增的視覺語彙**，
  而它非有不可（見 §5 第三條）
- 不新增字型、不新增第二套圓角與間距

### 6.3 Windows 優先

服務註冊（`hub-service.ps1`）本來就限 Windows，前景執行才跨平台。介面在
非 Windows 上該把服務相關的操作**藏起來而不是顯示為失敗**——那不是壞掉，
是這台機器沒有那個東西。

## 七、非目標

- 不做 Hub 的內容管理（房間、訊息、成員）——那是桌面 App 的事
- 不做多 Hub 實例的統一管理台
- 不做遠端管理（這個介面只在 Hub 那台機器上跑）
- 不做 named tunnel 的自動化（需要 Cloudflare 帳號與網域，不在一鍵範圍）
- **不動 `serve` / `funnel`**（`docs/DEPLOY-RESEARCH.md` 的紅線，不可推翻）
- 介面語言：**繁體中文**
