# Board — 設計簡報（Design Brief）

> 給 UI/UX 設計師的功能入門文件。
>
> ⚠️ **Board 不是獨立 App，但是獨立、可持續的工作實體。**
> Chatroom 是臨時的討論／執行場域；多間 Chatroom 可掛在同一塊 Board。
> 房間封存或刪除不會封存或刪除 Board。
> 請先讀 `docs/DESIGN-BRIEF.md`（Chatroom 本體）再讀這份；視覺語彙、深色
> 模式、成員的種類色系都沿用既有那套，不要另起爐灶。

## 一、這是什麼

**Board 是跨越多次聊天、可長期留存的共同任務板。**

Chatroom 讓多個 AI agent 與人類在同一個房間裡對話。但對話會流走——
今天講定的事，三百則訊息之後沒有人找得回來，而 agent 每次重啟都會忘記
自己上一輪做到哪。Board 是那些對話的**沉澱物**：誰要做什麼、做到哪了、
哪些已經確認過沒問題。

使用情境是**長期開發**：需求討論、實作、除錯與驗收可能各自開不同房間，
但都在推進同一塊 Board。Board 讓「現在到底是什麼狀況」變成一眼的事，
不要求某間房永遠保持開啟。

不是每間聊天室都要有 Board。短暫對話可以完全不掛；需要沉澱成持久工作時，
才建立 Board 或掛到既有 Board。

**它不取代聊天，也不取代釘選**。釘選是「這段話很重要」（訊息的屬性），
Board 是結構化的任務（獨立的東西）。三者並存。

## 二、核心概念與詞彙

三層，嚴格的樹狀結構：

| 詞彙 | 意義 | 例 |
|------|------|-----|
| **Objective（週期目標）** | 一個**週期**——一次可交付的成果。可以同時有好幾條在跑 | 「Board 功能上線」 |
| **Checklist（階段）** | 週期底下的階段分組 | 「Hub 端」「App 端」「測試與除錯」 |
| **Task（任務）** | 葉節點，**一個人做得完的一件事** | 「board 讀取端點」 |

Task 上還有兩組彼此獨立的資訊：

| 詞彙 | 意義 |
|------|------|
| **狀態** | 這件事進行到哪：待辦 / 進行中 / 卡住 / 完成 / 取消 |
| **認領（Claim）** | **誰在這張卡上**。agent 自己領，一張卡同時只能一個人持有 |
| **孤兒（Orphaned）** | 持有者在這塊 Board 的所有掛接房間都已沒有活動身分，並超過 grace period。離開其中一房不算孤兒 |
| **可撿回（Reclaimable）** | agent 重新回到 Board，看到自己上一次領走的孤兒卡。**不會自動認回** |
| **指派對象** | 人類可以指定「這張建議給誰做」。**是建議不是鎖**——被指定的人沒醒著時，別人仍可以認領 |
| **送審 / 確認 / 完成** | Objective 收尾的三段。agent 只能送審，**確認只有人類能按**，確認過才能完成 |
| **Supervisor（監督者）** | 可以指定一個 agent 接收整塊板的變動摘要。是 Board 層級角色，不屬於某間房 |

## 三、需要設計的畫面

平台與既有 App 相同：**Windows 桌面優先，Android 次之**，深色模式為主。

1. **Board Library**——獨立列出 active／archived Boards，不要求使用者先找到某間房。
2. **Board 主畫面**——以 Board 為路由的獨立全頁（不是側欄）。
   需要處理的資訊層次：目前在看哪一個 Objective、它底下有哪些階段、
   每個階段裡的卡。同時可能有 3～5 個 Objective 在跑。
3. **Task 卡片**——這份簡報最重要的一塊，見第四節。
4. **Task 詳情**——標題、描述、狀態、優先度、持有者、指定對象、
   「從哪間房的哪則訊息長出來」（原房尚在時可跳回）。
5. **建立與編輯**——人類手動加 Objective / Checklist / Task；
   從某則聊天訊息直接開一張卡。
6. **Objective 的收尾流程**——送審 → 確認 → 完成三段的視覺呈現。
   要看得出「現在卡在哪一段、等誰」。
7. **孤兒與可撿回的提示**——見第四節。
8. **聊天室裡的入口**——未掛時顯示建立／掛接；已掛時顯示 Board 名稱與
   待處理 badge（孤兒卡、等你確認的 Objective）。
9. **掛接的 Chatrooms**——Board 頁能看到哪些房正在使用它，並可切回來源對話。
10. **Supervisor 的設定與現況**——誰在監督、怎麼取消。

## 四、設計上值得思考的點

- **一張卡要同時講兩件事，而它們是正交的**：這件事「進行到哪」（狀態），
  以及「誰在上面、他還在不在」（認領）。把兩者混成一條進度條會讓
  「做到一半但人不見了」跟「還沒人碰」長得一模一樣——**而那正是最需要被
  看見的一種卡**。這是整個 Board 視覺上最難也最關鍵的一題。
- **孤兒卡是主角不是例外**。agent 會閒置、會被換掉、會 session 結束，
  這在這個系統裡是日常。一張看起來有人在做、實際上沒有的卡，價值全在於
  有人注意到它。它需要一個「有人做過但現在沒人」的視覺狀態，
  而不只是一個小標籤。
- **誰在這張卡上要一眼認得出**：沿用既有的成員種類色與徽章
  （claude / codex / human 各有顏色）。持有者離開之後名字仍然留著——
  「上一個是誰」是接手的人最需要知道的一件事。
- **人類與 agent 的權限差別要看得出來，而不是按了才知道**。
  「確認 Objective」只有人類能按，agent 的畫面上不該出現那顆按鈕。
- **認領會失敗，而且失敗是正常的**。兩個 agent 同時想領同一張卡，
  只有一個會成功。另一個要拿到的是「已經被 X 領走了」這個事實，
  不是一個錯誤畫面。
- **這塊板大部分時間是 agent 在動它**。人類多半在**看**：現在誰在做什麼、
  有沒有卡住、有沒有東西等我確認。「掃視」比「操作」重要。
- **與多間聊天室的往返**：Task 可指回長出它的特定房間與訊息。
  原房被刪除後仍顯示來源快照，但不假裝還能跳轉。
- **兩種封存要明確區分**：room 封存只代表這次對話唯讀；Board 可能仍在別房活躍。
  只有 Board 自己封存時，整塊板才使用「去飽和 + 唯讀告示」。
- **未掛接不等於空板**：聊天室默認沒有 Board。要設計「建立新板／掛既有板」，
  另外才是已建 Board 但尚無內容的 empty state。

## 五、限制與非目標

- **不要重新設計 Chatroom 本體**。Board 是併進去的一塊，配色、字型、
  深色模式、成員徽章、房間色系全部沿用既有的設計語言。
- 不需要設計：甘特圖／時間軸排程、工時估計、跨 **Board** 的組合看板、
  週期的自動化排程、任何形式的統計報表（皆為非目標）。
- 拖曳排序**可以**設計，但要能退回沒有拖曳的操作路徑（行動裝置）。
- 介面語言：**繁體中文**。
- 不需要 onboarding 或企業多租戶系統；但仍要表現 Board owner／editor／viewer
  以及人類／agent 的操作差異。
