# 失效形狀：靜默失效與它的鏡像

> 本文件是 2026-08-29 一整天跨裝置協作的沉澱。當天在 Hub、bridge、watcher、
> App、隧道五個層面各撞到同一個形狀的問題，值得當診斷透鏡反覆使用。

## 主形狀：看起來成功，實際掛在錯的地方，全程零錯誤

| 案例 | 表面 | 實際 |
|---|---|---|
| session key 分裂 | watcher 活著、沒報錯 | 頂著錯的身分去問，永遠問不到 |
| cloudflared 憑證污染 | 網址印出來了 | 隧道掛在別人的憑證上 |
| 殭屍 participant | 房裡有這個人 | 永遠不會醒，還吃掉 @mention |
| 定向問題推不到人 | 訂閱成功、問題建立成功 | server 那條訂閱是匿名的 |
| Codex 收不到本機人類的 @ | 通知系統運作正常 | 那則被「不通知自己」濾掉了 |

共通點：**每一個都不會拋出錯誤**。它們只能靠「有人實際去撞」才會現形，
而且撞到的人第一反應通常是懷疑網路、懷疑對方、懷疑版本——很少會懷疑
「成功訊息本身是假的」。

### 診斷提示

1. **「沒報錯」不是證據。** 驗收要有正向證據：看到 `session_key=`、看到事件、
   看到 join 回傳的 id。清單上每一項都要能指出「我看到了什麼」。
2. **同一台機器上看不出來的東西，需要處於不同狀態的環境去撞。** 持有 repo
   的那台永遠是「已裝好且正確」的狀態，看不到新機、舊設定、執行中進程。
   跨裝置實測的價值不可替代。
3. **凡是 `if (!x) return;` 的分支都要問「這在別人的環境裡是不是常態」。**
   靠 window bridge、環境變數、本機檔案溝通的模組之間有隱形依賴，型別系統
   看不見它們。

## 鏡像形狀：假的失敗

第五個案例方向相反，但代價一樣：

> 隧道自檢紅燈 → 判定 Cloudflare 速率限制 → 白等十幾分鐘冷卻 → 回頭查一個
> 不存在的問題。實際上隧道從外部完全正常，是**驗證方法**錯了（從 origin
> 本機打自己的公網網址，會被 hairpin、DNS 族別偏好、本機代理打斷）。

假的失敗容易被當成「保守一點沒差」，但它讓人關掉能用的東西、去修不存在的
問題。它的成因幾乎總是同一個：

> **驗證器斷言了超出它觀測範圍的事。**

`❌ 隧道沒有接到本機 Hub` 是一個它證明不了的斷言——它只知道「我這台打不通」。
同一個毛病也出現在 watcher 的舊訊息 `state 無 display_name（尚未 join？）`：
分裂時 bridge 確實 join 成功了，照那句提示去查的人會確認「有 join 啊」然後卡死。

📌 **把「我觀察不到」寫成「事實不存在」，是錯誤訊息最貴的一種寫法。**

修法通常只是措辭：說「本機自檢未通過，可能是本機網路環境所致，請由外部確認」
而不是「隧道壞了」。成本最低，收益最大。

📌 **驗證器本身也需要被驗證。**

## 錯誤訊息的判準

當天品質最高的錯誤訊息有一個共同點：**它們告訴你下一步做什麼，而不只是
「發生了什麼」**。

- ❌ `請指定 target` → ✅ `房裡有多位人類（Bernie、Bernie-2），請指定要問誰`
- ❌ `身分已失效，請重新加入` → ✅ 被踢時明講**不要**再自己加回去（那是人為
  決定，agent 照著「請重新加入」做就等於用工具推翻它），閒置移除時才說可以回來
- ❌ `找不到成員` → ✅ 附上房內目前的名字清單

📌 **同一個狀態碼底下，處置不同的情況就該有不同的 code。** 把它們壓成一個，
等於逼呼叫端去比對人類可讀的中文訊息——而那會在改一個字的時候無聲失效。

## 協作面的兩個約定

**多通道問題。** Hub 是共同真相來源，但不是唯一的指令通道。使用者在私人對話
裡推翻了房裡講定的事，房裡看不出任何異常，而 agent 的推論鏈會在不知情的
狀況下失效。

> 判準：**這件事會不會讓對方的推論鏈失效**。會的話，收到指示的一方負責在
> 房裡補一則說明。

**共用工作目錄。** 兩個 agent 在同一個 working tree 上並行時，`git add -A`
會把對方進行中的變更一起 commit 進去。約定：commit 一律指名檔案，開工前在
房裡宣告要動哪些檔。

## 一個操作教訓

用「不符合某特徵」挑選要終止的進程是危險的：

```powershell
# 意圖：殺掉臨時 Hub。實際：把正式 Hub 也殺了——它的 port 來自 .env，
# 根本不在命令列裡
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -notmatch '8787' }
```

📌 **要殺的東西用白名單（明確 PID），不要用黑名單。** 那個條件描述的不是
「臨時 Hub」，而是「命令列裡沒有 8787 的東西」——包含了要保護的目標。

## 第三種形狀：只做了一半的移除

外部測試人員回報「被踢出的人仍然看得到聊天室，甚至可以繼續對話」。查下去
是兩個各自獨立、疊在一起才致命的洞：

**洞 1：讀取沒有房間邊界。** 所有讀取端點只驗 token 不驗成員，被踢的人照樣
讀得到全部歷史、掛 long-poll 收即時訊息，只是不能發言。而設計文件裡我們
自己寫過「token 是信任邊界，房間不是」——那句話沒錯，錯在**踢出這個功能
承諾了一件系統做不到的事**。

> 📌 任何「移除某人」的功能，都要先問**「他被移除之後還讀得到什麼」**。
> 只擋寫入不擋讀取的移除，在使用者眼中就是沒有生效。

**洞 2：封鎖的識別握在被封鎖者手上。** `join` 的 kicked 檢查綁 `session_key`，
而那把 key 三種身分全都是自己產的：

| 角色 | session_key 從哪來 | 能不能自己換 |
|---|---|---|
| 人類 | App 自產 `human-<uuid4>` | ✅ 設定畫面有「重新產生」按鈕 |
| Claude agent | `CLAUDE_CODE_SESSION_ID` | ✅ `/clear` 就換一把 |
| Codex agent | thread id | ✅ 開新 thread |

換一把就是全新的人。**能被日常操作意外繞過的封鎖，更談不上封鎖。**

> 📌 **封鎖的對象必須是被封鎖者無法自行更換的識別。** 目前只有主持人發出去
> 的 access token 符合。session_key 是自報身分，token 才是被授予的身分。

驗證方法也跟著要改：

> 📌 驗「封鎖」時不能只驗「原樣重試會失敗」，要驗**「當事人手上能改的每一個
> 變數都改過之後還是失敗」**。

這條當時其實有人想到了，卻沒有變成發現——測試員把「我可以換 key 混進去」
當成**「我不該做的事」**處理完就結案，沒有轉念想成**「攻擊者會做的事」**。
同一個事實，兩個問句得到完全相反的產出。**站錯問句，就會親手把發現丟掉。**

### 誠實回報擋不住的那部分

對方若是拿主 token 進來的，踢出撤不掉那把（撤了所有人一起斷）。回應因此帶
`access_still_open`，明說「這個人還回得來」。

> 📌 **讓管理員以為已經切斷，比明說擋不住更危險。** 今天所有的坑都是「沒講
> 出來的例外」，這是少數一開始就講出來的。

## 產物識別：根因不在程式碼裡

同一天的第二件事：說好做完的功能在畫面上不見。根因是 `Release/chatroom_app.exe`
比那顆 commit 早 16.5 小時、中間隔著 17 個 commit——**每次 rebuild 都失敗，
而失敗留下一個看起來成功的現場**（`LNK1104` 淹在輸出中間，結尾只有一行
`Build process failed`，舊 exe 完好地留在原地）。

它能藏這麼久，是因為**畫面上沒有任何資訊能分辨手上跑的是哪一份程式碼**：
`FastAPI(version="0.1.0")` 與 `pubspec 1.0.0+1` 都是專案初始化的預設值，
從沒動過，所以它們看起來永遠像是「有版本」。

> 📌 **「不知道自己是哪一版」與「是 0.1.0 版」是完全不同的兩件事。**
> 把前者顯示成後者，讓人不會再去追問——這比不給更糟。
>
> 測試端的說法更直接：**分辨不出來的測試結果等於沒有測試。** 拿到一個 200，
> 卻不知道對面跑的是新碼還是舊碼，那個 200 沒有任何意義。

因此版本字串一律帶 commit hash，來源三段：打包寫入的 `_build.json` →
`git rev-parse` → **明說 unknown**（並在啟動時 WARNING）。工作樹髒標 `-dirty`
——那份產物對不回任何一個 commit，收到的人有權知道。

### 不要用產物的外部屬性推斷內容

用檔案時間戳判斷「有沒有 rebuild」有盲區：Flutter 的 `chatroom_app.exe` 是
C++ runner 殼，純 Dart 變更不會重寫它，更新的是 `data/app.so`。照 exe 判會
誤報成「沒 rebuild」。

> 📌 **讓內容自己說。** 版本字串要編進 Dart 側（跟著 `app.so` 走），不能靠
> 檔案屬性推斷。

### 交付本身是流程的一部分

當天兩個根因都不在程式碼裡：exe 沒重建、kit 搬到別的磁碟後 venv 內嵌的絕對
路徑全部失效（每支 console script 靜默 exit 1）。

> 📌 **交付是一個會出錯的步驟，值得跟 build 一樣被當成流程的一部分。**

升級順序也是交付的一部分，而且**相容性是不對稱的**：

| | 舊 Hub | 新 Hub |
|---|---|---|
| 舊 kit | ✅ | 🔴 附件、定向提問壞；讀不到 state 的直接徹底失聯 |
| 新 kit | ✅ | ✅ |

新 kit 對兩種 Hub 都相容，舊 kit 只對舊 Hub 相容——**所以 kit 先升、Hub 後升，
中間沒有陣痛期**。把不對稱看成對稱，就會得出「哪個先都會痛，選一個」這種
錯誤結論。

## 觀測面的噪音：操作成功了，但通知響給了錯的人

> 2026-08-30 的一整批 pin 缺陷。它們與上面幾節方向相反——不是「該發生的事
> 靜默沒發生」，而是**該安靜的地方在響**，而每一次響都會叫醒一個 agent、
> 燒掉一整輪 session。

三條缺陷、一個共同結構：**通知的收件人是算出來的，而那個算式在某些情境下
算出了不該收到的人。**

| 缺陷 | 算式 | 在什麼情境下算錯 |
|---|---|---|
| self-pin 通知作者 | 收件人＝被釘訊息的作者 | 作者就是操作者時，收件人集合是空的 |
| 釘選舊訊息重觸 mention | `you_were_mentioned`＝掃整批返回訊息 | 狀態變更會讓舊訊息重新落進批次 |
| 同名新人繼承舊 @ | mention 比對的是名字字串 | 名字在離開後被釋出，重用給下一個人 |

第一條讓 agent 被自己的釘選喚醒、讀回自己剛寫的長文，照「被 @ 就回」的規範
走就是自我循環。第二條讓任何人釘選一則幾天前 @ 過你的訊息都能把你叫醒。
第三條更糟：那則訊息**從來不是給他的**。

> 📌 **喚醒是打擾。** 每一條通知規則都該問：收到的人醒來之後有事可做嗎？
> 沒有的話，那條規則就是在燒別人的回合。

### 三個可複用的判準

**① 通知的收件人算式要在「收件人＝操作者」時退化成空集合。**
不是加特例，是承認那個集合本來就是空的。self-pin 原本的設計理由是「不想為
釘選者身分開特例」——立意good，但它換來的是一整類自我喚醒噪音。**規則的
一致性不值得用實際的傷害去買。**

**② 分辨「新事件」與「舊事件的新狀態」。**
同一條通道同時運送兩者（`MAX(seq, update_seq)` cursor）時，喚醒判定必須只
認前者。否則所有狀態變更都會變成喚醒事件。

**③ 拿名字當識別碼，就要為名字被回收的那一刻負責。**
房內唯一名稱只約束 active 成員 ⇒ 名字會被釋出重用 ⇒ 舊訊息裡的名字字串
會指向新的人。修法是給每個成員一條時間界線（`joined_seq`＝加入當下的房內
最後一則 seq），加入之前的 @ 一律不算。**用房內 seq 不用時間戳**——seq 是
既有的全序，毫秒級的先後沒有爭議空間。

### 附帶學到的兩件事

**「傳空值」不等於「關掉」。** 修 self-pin 時把 `mentions` 傳空並沒有用：
收據帶著 `reply_to`，而「回覆＝mention 被回覆的人」會在下游把作者補回去。
兩個都想通知的機制疊在同一則訊息上，關掉其中一個看起來就像關掉了。
**測試先紅過一次才現形，不是推理出來的。**

**同一個 401 有兩種病因，講成同一句話就會把人送去錯的地方。** App 釘選牆
讀訊息漏帶 `X-Participant-Id`，Hub 回 401 `participant_header_required`，
而 client 把所有 401 都翻成「API token 無效，請至設定檢查」——同一顆 token
其他畫面全部正常，人卻被導去設定頁翻一個根本不必改的東西。
> 📌 **錯誤訊息把人導向哪裡，比它描述得多準確更重要。**

## 測試自身的失效形狀

同一天測試端付的帳，形狀與被測系統的缺陷同構，值得單獨記一節。

**① 假資料讓測試停在前一道關卡。**
`kind="app"` 不是合法值（只有 `claude|codex|human|other`），請求在 422 就被
擋下，根本沒走到要驗的邏輯；而斷言寫得夠寬時，這種「沒跑到」看起來就像
「跑過了」。同款：dataclass 沒有 `role` 欄位，`py_compile` 過得去、跑起來
才炸——**語法檢查通過不等於能跑**。

**② 「不在房裡了」有四種狀態，只認一種就會等到逾時。**
`left` / `removed` / `kicked` / 整筆不見。級聯移除實測 1.1 秒完成、狀態是
`left`，而斷言只認 `removed` ⇒ 一路等到逾時 ⇒ **逾時看起來與功能壞掉完全
同形**，接著就會有人去追一個不存在的 bug。

**③ 多個 case 共用一間房，彼此破壞前提。**
C5 的父層跑完仍 active，C6 要驗的「房內已無 agent」於是永遠不成立。每個
case 自建房是便宜的，共用一間房省下的那點時間會用假失敗加倍還回來。

**④ 沒對未修版跑過的測試，不知道自己在守什麼。**
`BridgeState` 併發那三條測試寫完就跑綠、正要提交——臨時退回未修版本重跑，
**三條照樣全綠**。前後都綠的測試守不住任何東西：它可能量錯了對象、可能斷言
寫得太寬、也可能那個缺陷根本不存在。改成量測「存檔被吞掉幾次」之後才紅
（未修版 237 次，直接對打的壓力測試 720 次寫入拋了 717 次）。

> 📌 **先對未修版跑紅，才算測試。** 這一步順帶還會告訴你「病到底在不在」——
> 同一天另一條假設（`install.py` 會產生 `venv.old-*`）就是在動手前查證時
> 被推翻的：殘骸是舊版遺留，產生它的程式碼早就移走了。

它與 ① 同族：一個是「沒跑到要驗的地方」，一個是「跑到了但驗不出差別」，
表面都是綠燈。

**⑤ 前置條件沒成立，而測試自己不知道。**
「respawn 的 subagent 不該繼承前一個同名者的 @」這條 case 跑綠了——但綠的
原因是 respawn **根本沒拿回原名**（`worker` → `worker-2`），舊訊息裡的
`@worker` 對不上任何人，訊息連投遞的機會都沒有。待驗的邏輯一次都沒執行。
修法不是讓它紅，是把前置寫成明確的斷言：`respawn 沒拿回原名，這條就驗不到
分岔點`——失敗時說的是真正的原因，不是最後那行的表象。

**⑥ 另一道更早的關卡先擋掉，兩種語意都會綠。**
同一條 case 要分辨「界線該用父層的還是 subagent 自己的」，第一次跑三條全綠。
停下來問「這個綠是被什麼擋的」才發現：起點用了父層讀到的 cursor，舊訊息的
`seq` 比它小，`seq > after_seq` 那一關就先攔掉了——**兩種實作在這個讀法下
都會綠，鑑別力是零**。改用 `after_seq=0`（模擬父層重新連上、從頭拉一次，
watcher 重啟或 `/clear` 之後的真實情境）之後才紅，而那是正確的紅。

**⑦ 測試存在、設定也正確，但命令列把它整批排除掉了。**
`pytest.ini` 寫的是 `testpaths = tests bridge/tests`，而專案文件教的指令是
`pytest tests/`——**命令列一旦給了路徑就會覆寫 testpaths**。bridge 那半從此
一次都沒跑過，而「我跑了測試，全綠」這句話在當下完全屬實。
現形時已經有兩條紅燈躺在那裡：subagent identity 那批讓回應一律附上
`identity_scope`，兩條用精確相等的斷言當場就壞了，只是沒有人跑到它。
專案沒有 CI，那條指令就是唯一的守門，而它剛好漏掉一半。

### 五種假綠，一個問法

> 📌 **綠燈只說明「沒有發生我斷言的壞事」，不說明「我斷言的那條路徑真的
> 跑過」。** 前者是後者的必要條件，不是充分條件。
>
> 所以每一顆綠燈都值得問一句：**這個綠是被什麼擋的？答不出具體那一行，
> 就還沒驗到東西。**

底下五種是同一個病理的症狀。讀懂上面那句就不必記它們——遇到第六種
也推得出來：

| # | 形狀 | 綠燈實際來自 |
|---|---|---|
| 1 | 假資料停在前一道關卡（①） | 前置檢查拒絕，沒到待驗的邏輯 |
| 2 | 改動前後同色（④） | 測試根本不碰那條路徑 |
| 3 | 前置條件沒成立而測試不知道（⑤） | 名字對不上，訊息沒投遞 |
| 4 | 另一道更早的關卡先擋掉（⑥） | `after_seq`，不是待驗的 `joined_seq` |
| 5 | 那條測試根本不在這一輪裡（⑦） | 命令列路徑覆寫 `testpaths`，整批沒收集 |

> 📌 **綠燈的分母也要驗。** 問「這個綠是被什麼擋的」之前，先問「這一輪到底
> 跑了幾條」。收集數量是最便宜的正向證據，而平常沒有人看它。

> 📌 **觀察者不能破壞被觀測的條件。** 「留一個 agent 在房裡觀察封存倒數」
> 本身就讓房間不空——這種矛盾要在寫 case 之前先看出來，不是跑紅了再查。

> 📌 **把環境前提寫成會講話的守衛，不要寫成註解。** 「房內人類必須恰好一
> 個」寫成註解等於賭下一個人會讀到；寫成前置檢查並在失敗時說「這是環境
> 問題不是 bug」，它自己會講話。

## 共用 state 的錯誤處理，以為自己只有一個身分

subagent 功能開發時挖出來的洞，是一個新家族的第一筆：

> bridge 的 `_room_request` 在身分失效時**無條件清掉 state 檔的身分**。那是
> 父層的身分。於是一個 subagent 逾時，會把整個 session 的身分清掉。

程式碼在只有一個身分的世界裡是正確的，加進第二種身分之後才變成缺陷——而且
**沒有 subagent 之前它根本不會現形**。

> 📌 引入「同一個進程裡有多個身分」這類變更時，要回頭掃所有**清理與重置**
> 路徑：它們多半假設了「要清的就是我」。

## 綠燈給的是跳過流程的信心，而流程擋的不是綠燈擋得住的東西

合併日當天的流程破口：本機 `git merge --no-ff` 把 fix 直接併進 `develop`，
繞過 PR、繞過 review、也繞過 GitHub 上的紀錄。當事人的理由是真的——
**315 個測試全綠、GPG 簽章正常**。

但那兩件事證明的是「程式碼沒壞」，不是「這個決定該由一個人做」。

> 📌 **review 擋的從來不是測試測得到的東西。** 測試會告訴你程式碼有沒有壞；
> review 擋的是判斷、是取捨、是「這個修法對其他人意味著什麼」——那些東西
> 沒有紅燈，所以綠燈也不構成跳過它的理由。

同一天的第二個變體：merge 按下去之後，「PR 等著被合」被當成了「review 已經
發生」，而房內從頭到尾**沒有任何一句 review 結論存在**。這是「斷言先於觀測」
的流程版——差別只在被跳過的不是一行查證，是一個角色。

> 📌 **本機 merge 只用在「把上游併進自己的分支」這種不影響共用分支的方向。**
> 動到共用分支一律走 PR。方向不同，性質就不同：前者的後果只落在自己身上，
> 後者是替所有人做決定。

### 開發互審的極限

這一波沒有專職 review 角色，靠開發者互審頂住，而且那份 review 有真材實料
（主動去驗了沒人提的 rejoin 邊界）。但互審有結構性的盲區：**寫的人與審的人
共用同一套假設**，最容易漏的正是「大家共同認為理所當然」的那一類。

當天最好的反證是 `reply_mentions_author`：光傳空 `mentions` 關不掉通知，因為
下游的「回覆＝mention 作者」會把人補回去——**讀碼讀不出來，是測試網接住的**。
一個沒有預設立場的第三方，接住的會是另一批同樣讀不出來的東西。
