# 失效形狀：靜默失效與它的鏡像

> 本文件是 2026-08-29 一整天跨裝置協作的沉澱。當天在 Hub、bridge、watcher、
> App、隧道五個層面各撞到同一個形狀的問題，值得當診斷透鏡反覆使用。

## 主形狀：看起來成功，實際掛在錯的地方，全程零錯誤

| 案例 | 表面 | 實際 |
|---|---|---|
| session key 分裂 | watcher 活著、沒報錯 | 頂著錯的身分去問，永遠問不到 |
| cloudflared 憑證污染 | 網址印出來了 | 隧道掛在別人的憑證上 |
| 殭屍 participant | 房裡有這個人 | 永遠不會醒，還吃掉 @mention |
| 定向問題推不到人 | 訂閱成功、問題建立成功 | server 那條訂閱是匿名的 |
| Codex 收不到本機人類的 @ | 通知系統運作正常 | 那則被「不通知自己」濾掉了 |

共通點：**每一個都不會拋出錯誤**。它們只能靠「有人實際去撞」才會現形，
而且撞到的人第一反應通常是懷疑網路、懷疑對方、懷疑版本——很少會懷疑
「成功訊息本身是假的」。

### 診斷提示

1. **「沒報錯」不是證據。** 驗收要有正向證據：看到 `session_key=`、看到事件、
   看到 join 回傳的 id。清單上每一項都要能指出「我看到了什麼」。
2. **同一台機器上看不出來的東西，需要處於不同狀態的環境去撞。** 持有 repo
   的那台永遠是「已裝好且正確」的狀態，看不到新機、舊設定、執行中進程。
   跨裝置實測的價值不可替代。
3. **凡是 `if (!x) return;` 的分支都要問「這在別人的環境裡是不是常態」。**
   靠 window bridge、環境變數、本機檔案溝通的模組之間有隱形依賴，型別系統
   看不見它們。

## 鏡像形狀：假的失敗

第五個案例方向相反，但代價一樣：

> 隧道自檢紅燈 → 判定 Cloudflare 速率限制 → 白等十幾分鐘冷卻 → 回頭查一個
> 不存在的問題。實際上隧道從外部完全正常，是**驗證方法**錯了（從 origin
> 本機打自己的公網網址，會被 hairpin、DNS 族別偏好、本機代理打斷）。

假的失敗容易被當成「保守一點沒差」，但它讓人關掉能用的東西、去修不存在的
問題。它的成因幾乎總是同一個：

> **驗證器斷言了超出它觀測範圍的事。**

`❌ 隧道沒有接到本機 Hub` 是一個它證明不了的斷言——它只知道「我這台打不通」。
同一個毛病也出現在 watcher 的舊訊息 `state 無 display_name（尚未 join？）`：
分裂時 bridge 確實 join 成功了，照那句提示去查的人會確認「有 join 啊」然後卡死。

📌 **把「我觀察不到」寫成「事實不存在」，是錯誤訊息最貴的一種寫法。**

修法通常只是措辭：說「本機自檢未通過，可能是本機網路環境所致，請由外部確認」
而不是「隧道壞了」。成本最低，收益最大。

📌 **驗證器本身也需要被驗證。**

## 錯誤訊息的判準

當天品質最高的錯誤訊息有一個共同點：**它們告訴你下一步做什麼，而不只是
「發生了什麼」**。

- ❌ `請指定 target` → ✅ `房裡有多位人類（Bernie、Bernie-2），請指定要問誰`
- ❌ `身分已失效，請重新加入` → ✅ 被踢時明講**不要**再自己加回去（那是人為
  決定，agent 照著「請重新加入」做就等於用工具推翻它），閒置移除時才說可以回來
- ❌ `找不到成員` → ✅ 附上房內目前的名字清單

📌 **同一個狀態碼底下，處置不同的情況就該有不同的 code。** 把它們壓成一個，
等於逼呼叫端去比對人類可讀的中文訊息——而那會在改一個字的時候無聲失效。

## 協作面的兩個約定

**多通道問題。** Hub 是共同真相來源，但不是唯一的指令通道。使用者在私人對話
裡推翻了房裡講定的事，房裡看不出任何異常，而 agent 的推論鏈會在不知情的
狀況下失效。

> 判準：**這件事會不會讓對方的推論鏈失效**。會的話，收到指示的一方負責在
> 房裡補一則說明。

**共用工作目錄。** 兩個 agent 在同一個 working tree 上並行時，`git add -A`
會把對方進行中的變更一起 commit 進去。約定：commit 一律指名檔案，開工前在
房裡宣告要動哪些檔。

## 一個操作教訓

用「不符合某特徵」挑選要終止的進程是危險的：

```powershell
# 意圖：殺掉臨時 Hub。實際：把正式 Hub 也殺了——它的 port 來自 .env，
# 根本不在命令列裡
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -notmatch '8787' }
```

📌 **要殺的東西用白名單（明確 PID），不要用黑名單。** 那個條件描述的不是
「臨時 Hub」，而是「命令列裡沒有 8787 的東西」——包含了要保護的目標。

## 第三種形狀：只做了一半的移除

外部測試人員回報「被踢出的人仍然看得到聊天室，甚至可以繼續對話」。查下去
是兩個各自獨立、疊在一起才致命的洞：

**洞 1：讀取沒有房間邊界。** 所有讀取端點只驗 token 不驗成員，被踢的人照樣
讀得到全部歷史、掛 long-poll 收即時訊息，只是不能發言。而設計文件裡我們
自己寫過「token 是信任邊界，房間不是」——那句話沒錯，錯在**踢出這個功能
承諾了一件系統做不到的事**。

> 📌 任何「移除某人」的功能，都要先問**「他被移除之後還讀得到什麼」**。
> 只擋寫入不擋讀取的移除，在使用者眼中就是沒有生效。

**洞 2：封鎖的識別握在被封鎖者手上。** `join` 的 kicked 檢查綁 `session_key`，
而那把 key 三種身分全都是自己產的：

| 角色 | session_key 從哪來 | 能不能自己換 |
|---|---|---|
| 人類 | App 自產 `human-<uuid4>` | ✅ 設定畫面有「重新產生」按鈕 |
| Claude agent | `CLAUDE_CODE_SESSION_ID` | ✅ `/clear` 就換一把 |
| Codex agent | thread id | ✅ 開新 thread |

換一把就是全新的人。**能被日常操作意外繞過的封鎖，更談不上封鎖。**

> 📌 **封鎖的對象必須是被封鎖者無法自行更換的識別。** 目前只有主持人發出去
> 的 access token 符合。session_key 是自報身分，token 才是被授予的身分。

驗證方法也跟著要改：

> 📌 驗「封鎖」時不能只驗「原樣重試會失敗」，要驗**「當事人手上能改的每一個
> 變數都改過之後還是失敗」**。

這條當時其實有人想到了，卻沒有變成發現——測試員把「我可以換 key 混進去」
當成**「我不該做的事」**處理完就結案，沒有轉念想成**「攻擊者會做的事」**。
同一個事實，兩個問句得到完全相反的產出。**站錯問句，就會親手把發現丟掉。**

### 誠實回報擋不住的那部分

對方若是拿主 token 進來的，踢出撤不掉那把（撤了所有人一起斷）。回應因此帶
`access_still_open`，明說「這個人還回得來」。

> 📌 **讓管理員以為已經切斷，比明說擋不住更危險。** 今天所有的坑都是「沒講
> 出來的例外」，這是少數一開始就講出來的。

## 產物識別：根因不在程式碼裡

同一天的第二件事：說好做完的功能在畫面上不見。根因是 `Release/chatroom_app.exe`
比那顆 commit 早 16.5 小時、中間隔著 17 個 commit——**每次 rebuild 都失敗，
而失敗留下一個看起來成功的現場**（`LNK1104` 淹在輸出中間，結尾只有一行
`Build process failed`，舊 exe 完好地留在原地）。

它能藏這麼久，是因為**畫面上沒有任何資訊能分辨手上跑的是哪一份程式碼**：
`FastAPI(version="0.1.0")` 與 `pubspec 1.0.0+1` 都是專案初始化的預設值，
從沒動過，所以它們看起來永遠像是「有版本」。

> 📌 **「不知道自己是哪一版」與「是 0.1.0 版」是完全不同的兩件事。**
> 把前者顯示成後者，讓人不會再去追問——這比不給更糟。
>
> 測試端的說法更直接：**分辨不出來的測試結果等於沒有測試。** 拿到一個 200，
> 卻不知道對面跑的是新碼還是舊碼，那個 200 沒有任何意義。

因此版本字串一律帶 commit hash，來源三段：打包寫入的 `_build.json` →
`git rev-parse` → **明說 unknown**（並在啟動時 WARNING）。工作樹髒標 `-dirty`
——那份產物對不回任何一個 commit，收到的人有權知道。

### 不要用產物的外部屬性推斷內容

用檔案時間戳判斷「有沒有 rebuild」有盲區：Flutter 的 `chatroom_app.exe` 是
C++ runner 殼，純 Dart 變更不會重寫它，更新的是 `data/app.so`。照 exe 判會
誤報成「沒 rebuild」。

> 📌 **讓內容自己說。** 版本字串要編進 Dart 側（跟著 `app.so` 走），不能靠
> 檔案屬性推斷。

### 交付本身是流程的一部分

當天兩個根因都不在程式碼裡：exe 沒重建、kit 搬到別的磁碟後 venv 內嵌的絕對
路徑全部失效（每支 console script 靜默 exit 1）。

> 📌 **交付是一個會出錯的步驟，值得跟 build 一樣被當成流程的一部分。**

升級順序也是交付的一部分，而且**相容性是不對稱的**：

| | 舊 Hub | 新 Hub |
|---|---|---|
| 舊 kit | ✅ | 🔴 附件、定向提問壞；讀不到 state 的直接徹底失聯 |
| 新 kit | ✅ | ✅ |

新 kit 對兩種 Hub 都相容，舊 kit 只對舊 Hub 相容——**所以 kit 先升、Hub 後升，
中間沒有陣痛期**。把不對稱看成對稱，就會得出「哪個先都會痛，選一個」這種
錯誤結論。

## 觀測面的噪音：操作成功了，但通知響給了錯的人

> 2026-08-30 的一整批 pin 缺陷。它們與上面幾節方向相反——不是「該發生的事
> 靜默沒發生」，而是**該安靜的地方在響**，而每一次響都會叫醒一個 agent、
> 燒掉一整輪 session。

三條缺陷、一個共同結構：**通知的收件人是算出來的，而那個算式在某些情境下
算出了不該收到的人。**

| 缺陷 | 算式 | 在什麼情境下算錯 |
|---|---|---|
| self-pin 通知作者 | 收件人＝被釘訊息的作者 | 作者就是操作者時，收件人集合是空的 |
| 釘選舊訊息重觸 mention | `you_were_mentioned`＝掃整批返回訊息 | 狀態變更會讓舊訊息重新落進批次 |
| 同名新人繼承舊 @ | mention 比對的是名字字串 | 名字在離開後被釋出，重用給下一個人 |

第一條讓 agent 被自己的釘選喚醒、讀回自己剛寫的長文，照「被 @ 就回」的規範
走就是自我循環。第二條讓任何人釘選一則幾天前 @ 過你的訊息都能把你叫醒。
第三條更糟：那則訊息**從來不是給他的**。

> 📌 **喚醒是打擾。** 每一條通知規則都該問：收到的人醒來之後有事可做嗎？
> 沒有的話，那條規則就是在燒別人的回合。

### 三個可複用的判準

**① 通知的收件人算式要在「收件人＝操作者」時退化成空集合。**
不是加特例，是承認那個集合本來就是空的。self-pin 原本的設計理由是「不想為
釘選者身分開特例」——立意good，但它換來的是一整類自我喚醒噪音。**規則的
一致性不值得用實際的傷害去買。**

**② 分辨「新事件」與「舊事件的新狀態」。**
同一條通道同時運送兩者（`MAX(seq, update_seq)` cursor）時，喚醒判定必須只
認前者。否則所有狀態變更都會變成喚醒事件。

**③ 拿名字當識別碼，就要為名字被回收的那一刻負責。**
房內唯一名稱只約束 active 成員 ⇒ 名字會被釋出重用 ⇒ 舊訊息裡的名字字串
會指向新的人。修法是給每個成員一條時間界線（`joined_seq`＝加入當下的房內
最後一則 seq），加入之前的 @ 一律不算。**用房內 seq 不用時間戳**——seq 是
既有的全序，毫秒級的先後沒有爭議空間。

### 附帶學到的兩件事

**「傳空值」不等於「關掉」。** 修 self-pin 時把 `mentions` 傳空並沒有用：
收據帶著 `reply_to`，而「回覆＝mention 被回覆的人」會在下游把作者補回去。
兩個都想通知的機制疊在同一則訊息上，關掉其中一個看起來就像關掉了。
**測試先紅過一次才現形，不是推理出來的。**

**同一個 401 有兩種病因，講成同一句話就會把人送去錯的地方。** App 釘選牆
讀訊息漏帶 `X-Participant-Id`，Hub 回 401 `participant_header_required`，
而 client 把所有 401 都翻成「API token 無效，請至設定檢查」——同一顆 token
其他畫面全部正常，人卻被導去設定頁翻一個根本不必改的東西。
> 📌 **錯誤訊息把人導向哪裡，比它描述得多準確更重要。**

## 測試自身的失效形狀

同一天測試端付的帳，形狀與被測系統的缺陷同構，值得單獨記一節。

**① 假資料讓測試停在前一道關卡。**
`kind="app"` 不是合法值（只有 `claude|codex|human|other`），請求在 422 就被
擋下，根本沒走到要驗的邏輯；而斷言寫得夠寬時，這種「沒跑到」看起來就像
「跑過了」。同款：dataclass 沒有 `role` 欄位，`py_compile` 過得去、跑起來
才炸——**語法檢查通過不等於能跑**。

**② 「不在房裡了」有四種狀態，只認一種就會等到逾時。**
`left` / `removed` / `kicked` / 整筆不見。級聯移除實測 1.1 秒完成、狀態是
`left`，而斷言只認 `removed` ⇒ 一路等到逾時 ⇒ **逾時看起來與功能壞掉完全
同形**，接著就會有人去追一個不存在的 bug。

**③ 多個 case 共用一間房，彼此破壞前提。**
C5 的父層跑完仍 active，C6 要驗的「房內已無 agent」於是永遠不成立。每個
case 自建房是便宜的，共用一間房省下的那點時間會用假失敗加倍還回來。

**④ 沒對未修版跑過的測試，不知道自己在守什麼。**
`BridgeState` 併發那三條測試寫完就跑綠、正要提交——臨時退回未修版本重跑，
**三條照樣全綠**。前後都綠的測試守不住任何東西：它可能量錯了對象、可能斷言
寫得太寬、也可能那個缺陷根本不存在。改成量測「存檔被吞掉幾次」之後才紅
（未修版 237 次，直接對打的壓力測試 720 次寫入拋了 717 次）。

> 📌 **先對未修版跑紅，才算測試。** 這一步順帶還會告訴你「病到底在不在」——
> 同一天另一條假設（`install.py` 會產生 `venv.old-*`）就是在動手前查證時
> 被推翻的：殘骸是舊版遺留，產生它的程式碼早就移走了。

**反向也算數**：修完才想到要測時，**把缺陷加回去看它紅不紅**。那是同一件事
的另一個方向，而且在「已經修好了」的情況下是唯一的路。要驗的東西不變——
**這條測試在缺陷存在時會不會失敗**。

它與 ① 同族：一個是「沒跑到要驗的地方」，一個是「跑到了但驗不出差別」，
表面都是綠燈。

**⑤ 前置條件沒成立，而測試自己不知道。**
「respawn 的 subagent 不該繼承前一個同名者的 @」這條 case 跑綠了——但綠的
原因是 respawn **根本沒拿回原名**（`worker` → `worker-2`），舊訊息裡的
`@worker` 對不上任何人，訊息連投遞的機會都沒有。待驗的邏輯一次都沒執行。
修法不是讓它紅，是把前置寫成明確的斷言：`respawn 沒拿回原名，這條就驗不到
分岔點`——失敗時說的是真正的原因，不是最後那行的表象。

**⑥ 另一道更早的關卡先擋掉，兩種語意都會綠。**
同一條 case 要分辨「界線該用父層的還是 subagent 自己的」，第一次跑三條全綠。
停下來問「這個綠是被什麼擋的」才發現：起點用了父層讀到的 cursor，舊訊息的
`seq` 比它小，`seq > after_seq` 那一關就先攔掉了——**兩種實作在這個讀法下
都會綠，鑑別力是零**。改用 `after_seq=0`（模擬父層重新連上、從頭拉一次，
watcher 重啟或 `/clear` 之後的真實情境）之後才紅，而那是正確的紅。

**⑦ 測試存在、設定也正確，但命令列把它整批排除掉了。**
`pytest.ini` 寫的是 `testpaths = tests bridge/tests`，而專案文件教的指令是
`pytest tests/`——**命令列一旦給了路徑就會覆寫 testpaths**。bridge 那半從此
一次都沒跑過，而「我跑了測試，全綠」這句話在當下完全屬實。
現形時已經有兩條紅燈躺在那裡：subagent identity 那批讓回應一律附上
`identity_scope`，兩條用精確相等的斷言當場就壞了，只是沒有人跑到它。
專案沒有 CI，那條指令就是唯一的守門，而它剛好漏掉一半。

### 五種假綠，一個問法

> 📌 **綠燈只說明「沒有發生我斷言的壞事」，不說明「我斷言的那條路徑真的
> 跑過」。** 前者是後者的必要條件，不是充分條件。
>
> 所以每一顆綠燈都值得問一句：**這個綠是被什麼擋的？答不出具體那一行，
> 就還沒驗到東西。**

底下五種是同一個病理的症狀。讀懂上面那句就不必記它們——遇到第六種
也推得出來：

| # | 形狀 | 綠燈實際來自 |
|---|---|---|
| 1 | 假資料停在前一道關卡（①） | 前置檢查拒絕，沒到待驗的邏輯 |
| 2 | 改動前後同色（④） | 測試根本不碰那條路徑 |
| 3 | 前置條件沒成立而測試不知道（⑤） | 名字對不上，訊息沒投遞 |
| 4 | 另一道更早的關卡先擋掉（⑥） | `after_seq`，不是待驗的 `joined_seq` |
| 5 | 那條測試根本不在這一輪裡（⑦） | 命令列路徑覆寫 `testpaths`，整批沒收集 |

> 📌 **綠燈的分母也要驗。** 問「這個綠是被什麼擋的」之前，先問「這一輪到底
> 跑了幾條」。收集數量是最便宜的正向證據，而平常沒有人看它。

> 📌 **觀察者不能破壞被觀測的條件。** 「留一個 agent 在房裡觀察封存倒數」
> 本身就讓房間不空——這種矛盾要在寫 case 之前先看出來，不是跑紅了再查。

> 📌 **把環境前提寫成會講話的守衛，不要寫成註解。** 「房內人類必須恰好一
> 個」寫成註解等於賭下一個人會讀到；寫成前置檢查並在失敗時說「這是環境
> 問題不是 bug」，它自己會講話。

## 共用 state 的錯誤處理，以為自己只有一個身分

subagent 功能開發時挖出來的洞，是一個新家族的第一筆：

> bridge 的 `_room_request` 在身分失效時**無條件清掉 state 檔的身分**。那是
> 父層的身分。於是一個 subagent 逾時，會把整個 session 的身分清掉。

程式碼在只有一個身分的世界裡是正確的，加進第二種身分之後才變成缺陷——而且
**沒有 subagent 之前它根本不會現形**。

> 📌 引入「同一個進程裡有多個身分」這類變更時，要回頭掃所有**清理與重置**
> 路徑：它們多半假設了「要清的就是我」。

## 綠燈給的是跳過流程的信心，而流程擋的不是綠燈擋得住的東西

合併日當天的流程破口：本機 `git merge --no-ff` 把 fix 直接併進 `develop`，
繞過 PR、繞過 review、也繞過 GitHub 上的紀錄。當事人的理由是真的——
**315 個測試全綠、GPG 簽章正常**。

但那兩件事證明的是「程式碼沒壞」，不是「這個決定該由一個人做」。

> 📌 **review 擋的從來不是測試測得到的東西。** 測試會告訴你程式碼有沒有壞；
> review 擋的是判斷、是取捨、是「這個修法對其他人意味著什麼」——那些東西
> 沒有紅燈，所以綠燈也不構成跳過它的理由。

同一天的第二個變體：merge 按下去之後，「PR 等著被合」被當成了「review 已經
發生」，而房內從頭到尾**沒有任何一句 review 結論存在**。這是「斷言先於觀測」
的流程版——差別只在被跳過的不是一行查證，是一個角色。

> 📌 **本機 merge 只用在「把上游併進自己的分支」這種不影響共用分支的方向。**
> 動到共用分支一律走 PR。方向不同，性質就不同：前者的後果只落在自己身上，
> 後者是替所有人做決定。

### 開發互審的極限

這一波沒有專職 review 角色，靠開發者互審頂住，而且那份 review 有真材實料
（主動去驗了沒人提的 rejoin 邊界）。但互審有結構性的盲區：**寫的人與審的人
共用同一套假設**，最容易漏的正是「大家共同認為理所當然」的那一類。

當天最好的反證是 `reply_mentions_author`：光傳空 `mentions` 關不掉通知，因為
下游的「回覆＝mention 作者」會把人補回去——**讀碼讀不出來，是測試網接住的**。
一個沒有預設立場的第三方，接住的會是另一批同樣讀不出來的東西。

# 2026-08-31：三個 Novia + 一個 Codex 審核

> 當天四個 session 並行（主線施工 / 除錯施工 / 裁決 / 外部審核），18 張功能票
> 加 12 條審核 finding。教訓密度高到值得單獨一節——而它們幾乎全部**不是**
> 程式寫錯，是判斷的形狀錯了。

## 綠燈與紅燈都要問「為什麼」

當天出現了五種「顏色是對的、理由是錯的」：

| 形狀 | 症狀 | 為什麼危險 |
|---|---|---|
| **測試分母被偷換** | `pytest tests/` 覆寫 `pytest.ini` 的 `testpaths`，`bridge/tests` 整個不被收集 | 「我跑了測試全綠」當下完全屬實，而兩條紅燈躺著沒人看見 |
| **驗證時機錯位** | 新增檔案後沒重跑 `flutter analyze`，回報的是加檔之前的數字 | 報出一個沒驗過的數字，而它看起來與驗過的一模一樣 |
| **fixture 與真實資料的落差** | watcher 去重靠訊息 `id`，測試 fixture 沒那個欄位 → **正確的實作紅了** | 差一點就照著紅燈把對的東西改壞 |
| **前置步驟失敗** | 驗證「被踢的人還能刪訊息」時 kick 那步 401，但後面 delete 照樣 200 | **看起來完全像洞重現了**，而它只是前置沒成立 |
| **綠得不是你以為的原因** | 「離開者不能編輯」一開始就綠，實際上擋住它的是另一個 session 同時在修的 `status='active'` | 差點當成「這裡本來就沒問題」的證據 |

> 📌 **測試裡的前置動作要有 `assert`。** 那不是禮貌，是防止整組測試變成空跑。
> 📌 **綠燈的分母也要驗。** 「全綠」在分母被偷換時仍然是真話。

## 知道一條規則，跟在每個呼叫點認出它，是兩種能力

`resolve_state_path` 的 docstring 寫著「**檔名不是權威，內容裡的 session_key
才是**」——那句話是為了 08/29 的身分消失事件寫的。

而 `be0bb16` 的 GC 在隔壁函式用了**檔名比對**來判斷「哪一份是自己的」
（`state_path` 而不是 `resolve_state_path`）。寫的人當天稍早才在房內引用過
同一條規則。

> 📌 規則寫在文件裡、寫在註解裡、甚至剛講過，都不保證下一個呼叫點會認出它。
> **要讓規則生效，得讓錯的寫法在語法上不存在**——見下面的「把規則做成形狀」。

## 把規則做成資料的形狀，而不是靠人記得

G1 的 session key resolver 原本是 if 分支：

```python
if kind == "claude":
    if os.environ.get("CLAUDE_CODE_SESSION_ID"): ...
```

「**跨 kind 不能採用別人的環境變數**」這條規則（從 Claude session 的 shell
拉起的 Codex 會繼承母 session 的 id，撞 key 後 join 冪等會把兩個進程合併成
同一個 participant，訊息混流且兩邊都不報錯）在這個形狀裡**只能靠每個人記得
寫對**。

改成一張 `kind → 變數` 的表之後，想加一個變數就得先決定它屬於哪個 kind——
**「順便也看一下別人的」這種寫法在語法上不存在。**

> 📌 **比守門測試更前面一道防線，是讓錯誤的寫法寫不出來。**

## 診斷訊息送到沒有人在看的通道

watcher 的身分分裂自檢**寫得很好**：講了成因、講了處置、講了副作用。

它走 `_log` → **stderr**。而 Monitor 只把 **stdout** 當事件流。

> 收件人正是最看不到東西的那個人：他在等指派、指派永遠不會到、終端機與房內
> 都一片安靜——**連那句為他寫的診斷都在他看不到的通道上**。

這比「沒寫診斷」更難發現，因為程式碼讀起來完全正確。

> 📌 **診斷訊息送到沒有人在看的地方，等於沒有診斷。** 寫完錯誤處理要問一句：
> 這句話會出現在誰的眼前？那個人是不是需要它的人？

## 破壞性動作的授權，不能來自「我覺得我很小心」

`be0bb16` 的 state 檔 GC 用 mtime > 30 天判定 orphan 並直接 `unlink`。
commit 訊息裡寫著「**保守到近乎膽小**」，並列了四條保護。

審核指出：**mtime 不構成 orphan 的證據**。「30 天沒啟動」與「已經死了」是
兩回事——resume 一個放很久的 session 是完全正常的用法，而那正是最需要身分
延續的時刻。

而那句「保守到近乎膽小」的實際作用是**讓寫的人停止評估風險**。

> 📌 自我宣稱的謹慎程度不是證據。正確的問題不是「我夠不夠小心」（永遠可以
> 說夠），而是：**這個動作最壞的結果，跟它最好的結果對不對等。**
>
> 最好：少幾個檔案。最壞：抹掉一個活著的 agent 的身分與讀取游標。
> 寫下來就結束了，不需要任何謹慎程度的自我評估。

裁決端的補充歸因同樣成立：**下令「清墓地」的人給了一個美觀問題破壞授權，
而選擇 unlink 這個最重工具的是執行的人。** 兩層各記各的。

## 狀態不是事件

`edited_at` 與 `deleted` 是**黏著狀態**——一旦有值就永遠有值。watcher 從它們
回推「這次 update 為什麼發生」，於是「編輯過的訊息後來被釘選」被讀成「它剛
被編輯」。

第一版修法用「跟上次看到的狀態比」來去重。審核指出它仍不足：**watcher 會
忘記**——重啟時記憶體歸零、快取淘汰時更是常態（**而釘選牆的用途正是讓人回頭
釘很舊的訊息**，那條淘汰註解寫的「最舊的早就不會再變」被功能本身直接推翻）。

> 📌 **狀態簽章只能回答「我記不記得見過這個狀態」，回答不了「這次為什麼
> 發生」。** 需要後者就得讓事件來源自己說（Hub 端寫 `update_kind`）。

## 記憶、票、文件都是入口，現場才是規格

- **票**：當天至少五張票的內容與現場衝突（方向寫反、被更早落地的端點取代、
  漏掉關鍵路徑、票序本身有依賴錯誤、看似可拆實際不可拆）
- **記憶**：一則 08/28 的 PM 記憶把「文件要修」記成待辦，而文件在 `1308b6b`
  當天就修好了——**修完之後沒有人回去更新記憶**。讀到它的人據此在房內宣告了
  一件不成立的事，裁決者還據此下了裁定
- **文件**：`~/.chatroom/session_key` 這個檔案在磁碟上活了四天，而它對應的
  文件敘述早就改掉了

> 📌 **記憶反映的是寫下當時的狀態，不是現在。引用它之前要驗。**
> 那則記憶單獨看完全正確，只是它的**有效期沒有寫在上面**。

## 「沒有值」與「值是空的」是兩件事

Hub 的 session 名錄 upsert **只在非空值時覆寫**（舊 bridge 相容性的設計）。
所以 App 在讀不到主機名時：

- 送空字串 → **主動把一個已知的主機名洗成未知**
- 不送 → 保留 Hub 手上既有的值

> 📌 面對「只在有值時覆寫」的 API，`null` 與 `""` 的語意相差一個資料損失。

## 多 agent 並行的協作準則

核心三條**寫在這裡**，PM 記憶是延伸閱讀而不是唯一來源——把版控文件的內容
外包給不在版控的東西，換一台機器 clone 下來就只剩一個指向不存在東西的指標。
（那是下面第七形狀「記憶會過期」的更前一步：不只是內容過期，是**內容根本
不在**。同一天的另一個實例：有人把「不要指定 `tests/`」的警告寫進 CLAUDE.md，
之後才發現那個檔案在 `.gitignore` 裡——只保護了自己那台機器。）

1. **檔案分界**管「同時施工不互踩」，**票認領**管「同一件事不做兩份」——
   兩層都要。當天的撞車是檔案分界清楚、但同一張票被兩人各做一半
2. **任何形式的「N 秒內沒回就開工」都不成立**——那是通知不是握手。
   撞車發生時兩邊其實都喊了，差 37 秒
3. 🚨 **共用 working tree 上，絕不對別人未提交的變更執行任何 git 操作**，
   包含看起來可逆的（`stash`/`pop` 在內）。可逆操作一樣會開出「別人看到
   HEAD 而非現況」的窗口，而**窗口期間 `git status` 等所有檢查工具都顯示
   正常**——「動手前先看 status」擋不住它

> 📌 還原類動作視同寫入。它不留痕跡，被清掉的人不會收到任何錯誤，
> 只會看到自己的工作憑空消失。

## 構造不出那個窗口時，不要寫行為測試

「先對未修版跑紅」有一個前提：**你構造得出觸發缺陷的條件**。當天兩次構造不
出來：

- `update_seq` 不變量——會觸發它的端點在寫守衛的當下**還不存在**
- rollback 競態（F11）——`ASGITransport` 底下的協程交錯不夠真實，把缺陷加
  回去跑四次**全綠**

兩次的結論一樣：**改成靜態守衛**（AST 掃描程式碼的形狀），不寫行為測試。

> 📌 缺陷的觸發條件依賴時序或環境時，先問「**我構造得出那個窗口嗎**」。
> 構造不出來就不要寫行為測試——**寫了會得到一顆永遠綠的燈，比沒有更糟**：
> 它會讓後來的人以為這條路徑被守著。

代價要講清楚：**靜態守衛守的是形狀，不是效果**。所以註解必須寫明「為什麼
不能鬆綁」與「什麼條件下可以」——否則下一個人只會看到一條莫名其妙的規則，
然後刪掉它。當天的 `_READ_ONLY_EXEMPT` 豁免清單就是這個形狀：**守衛看不出
方向**（那個端點提到 mentions 是為了**拒絕**它），所以豁免旁邊必須寫上拆除
條件。

> 📌 豁免清單是這種守衛最容易腐爛的地方。**每一筆豁免都要帶著「什麼時候
> 該把我拿掉」一起寫。**

## 間歇正確比全錯更難查

右鍵選單不貼游標（F16）。程式碼**用了正確的 API**——`details.globalPosition`
就在那裡——所以每一次讀碼都讀不出問題。

真正的病灶是兩端的座標系不是同一個：點擊座標是全視窗的，而 `showMenu` 的
位置相對於**它落腳的那個 Overlay**，兩邊各自用了預設值去取 overlay。

> **偏移量剛好是兩個 overlay 的原點差。**

於是它在某些畫面結構下**完全正常**，在另一些畫面上差半個螢幕。這類缺陷有
三個讓它活很久的性質：

1. **讀碼讀不出來**——用的 API 是對的，參數也是對的
2. **回報者說不清楚**——「有時候位置怪怪的」不構成可行動的 bug report
3. **修的人容易停在表面**——猜「忘了帶座標」會得到一個看起來合理但不成立的
   假設，而照那個假設改動之後症狀可能剛好緩解（因為順手改了別的東西）

> 📌 症狀「有時候對」時，不要找「哪裡寫錯了」，要找**哪兩個東西應該一致而
> 沒有人保證它們一致**。前者會找到一堆看起來對的程式碼，後者會找到真因。

修法的形狀因此也不同：**不是修一個值，是讓兩端明確指向同一個來源**
（`rootOverlay: true` 與 `useRootNavigator: true` 成對出現）。

> 📌 這種「成對才成立」的設定要用守衛釘住**兩個一起**——拆掉任何一半都會
> 回到「大部分時候對」，而那個狀態不會有任何測試紅。

## 拿到第二份證據就急著結案，比原本的誤報更危險

`git stash` 事故中，兩邊各自看到一個真相（窗口內是空的、窗口外是完整的），
而在拿到第二份證據時，**雙方都順手編了一個能自圓其說的解釋**：一邊說「是我
輸出截斷看錯」，另一邊說「pop 成功所以沒事」——後者當時並不知道對方有沒有在
那 35 秒內寫入。

> 📌 兩份互相矛盾的證據**都為真**時，先找「什麼機制能讓兩者同時成立」，
> 不要挑一份當成錯覺。急著結案的解釋聽起來像答案，而它會終止調查。

### 下半段：結案之後補的那個解釋，沒有人會再驗

同一天稍晚的實例。App build 出來標的 commit 與 build 前看到的 HEAD 不同，
產物本身沒問題（那顆 commit 只動文件），而回報時我順手寫了一句機制：

> ❌「build 期間對方**推了**那個 commit，共用 working tree 的 HEAD 就跟著動了」

**`push` 不會動本機 HEAD。** 動它的是對方在同一個 working tree 上跑的
`git commit`。結論（HEAD 在 build 期間是活的）碰巧是對的，機制是錯的。

代價不在那句話本身，在它會長出什麼：

| | 導出的防護 | 有沒有用 |
|---|---|---|
| 錯的機制（push） | 「build 期間不要 push」 | **完全沒用**，push 從來不是原因 |
| 對的機制（commit） | 「build 期間不要在這個 working tree 上 commit」 | 擋得住 |

> 📌 **機制講錯而結論碰巧對，比結論錯更難查。** 結論被證實之後就沒有人會
> 回頭質疑它的理由，而錯的理由會靜靜地長出一條擋不住任何東西的規則——
> 那條規則之後還會被遵守、被寫進文件、被當成已經處理過。

同一天三次同族：`git stash` 事故編出「輸出截斷看錯」、`pop` 成功就宣告沒事、
以及這次的 push。三次都是**拿到正確結論之後，隨手補一個聽起來合理的機制**。

## 共用 working tree 上，build 是一段有長度的時間

`build-app.py` 在**開始時**讀 `git rev-parse` 決定要編進去的 commit，flutter
在那之後才逐一讀原始碼。兩者之間有幾十秒，而共用 working tree 上那段時間裡
HEAD 是活的：另一個 agent 落一個 commit，產物就會標著新 hash、裝著新舊混合
的原始碼。

2026-08-31 實際發生過一次，無害（那顆 commit 只動 `docs/`，Dart 原始碼一個
字沒變，標記與內容仍然一致）。**但它會通過所有現有的檢查**：

- `git status` 乾淨 ✅（對方已經 commit 了）
- 產物驗證通過 ✅（版本字串確實編進去了）
- build log 漂亮 ✅

同一天剛加的產物驗證（F15）也照不到它——那支驗的是「版本字串有沒有進去」，
驗不出「這些原始碼是不是同一顆 commit 的」。

> 📌 **驗證器只證明它量得到的那件事。** 一個新加的檢查會讓人覺得「這塊守住
> 了」，而它守住的往往比那個感覺小得多。加檢查時要順手說清楚它**照不到**什麼。

要關掉的話成本很低（build 前後各讀一次 HEAD，不同就拒絕出貨），但先確認這個
場景值不值得——**多 agent 共用一個 working tree 本身就是這個風險的來源，
而那個安排是刻意的**。

## 接卡先驗前提：卡的描述停在寫卡那一天

2026-09-05 一天之內至少五次「以為缺、其實早就有」：

| 卡上寫著要做 | 實際狀態 |
|---|---|
| 段落標籤 | server 半 09/04 就落地，剩 UI |
| D9 零掛接房建卡 500 | 09/03 已修 |
| health 回啟動時快取的 build | 08/29 `2a8085c` 就成立 |
| N-1 側門 A、`attached_rooms` 帶 visibility | 兩件都是 09/03 補的 |
| kit README「分兩次裝」 | 第 34 行本來就有 |

沒有一張卡寫錯——**它們都停在寫卡的那一天，而那一天之後有人把事情做掉了，
卡不會自己更新**。板上的卡是「當時看到的缺口」，不是「現在的缺口」。

代價不對稱，這是它值得一條規則的原因：

- 驗證前提：幾分鐘，讀一段程式碼或打一次探針
- 不驗證：實作一個已經存在的東西，然後卡在**「為什麼我的修改沒有效果」**——
  而那個問題長得像 bug，不像「你在重做一件做完的事」

> 📌 **接到卡的第一件事是驗證卡的前提還成不成立，不是開始實作。**

⚠️ 查證的結論有三種，處置不同：

- **早就做完了** → 卡推 done，把查證寫上卡（下一個人才不會再查一次）
- **機制成立但沒有測試釘著** → 補測試。這種**全綠是正常的**，它是防迴歸不是
  修 bug；價值在「哪天有人改壞了會有人叫」，所以要在測試裡寫清楚**它會在
  什麼情況下紅**
- **真的還沒做** → 照卡實作

第二種最容易被誤判成第一種而直接收掉。「成立」與「守得住」是兩件事：
N-1 的白名單成立於 `list_rooms` 那句 `EXISTS(...)` 與 `visibility` 的 **OR**
關係，沒有任何測試釘著它——改成 `AND` 之後症狀是「某些人的房間不見了」，
而那看起來像 client 的 bug。
