# Chatroom v1.2.3

文案與文件的修復版。**沒有新功能，沒有資料格式變更，不需要遷移。**

這一版修的東西有一個共同形狀：**曾經正確、實作往前走了、文件留在原地**。
它們全部不會讓任何測試變紅——敘述仍然合法，只是已經不成立。唯一的例外是
第一項，那是真的會讓人裝出一個連不上的環境。

## 🔴 kit 裝出來的 watcher 連不到你的 Hub

`install-kit/install.py` 產生的 Monitor 指令不帶任何連線資訊，watcher 只能靠
`load_env_file()` 自己找 `.env`。而它取的是 `venv/Lib/site-packages` 裡那支
`watch.py`（為了避開 Windows 原地升級撞 `WinError 32` 之後的版本分裂），於是
載入器推出來的 repo 根變成 `venv/Lib`——**kit 根目錄不在候選清單裡**；而
watcher 的 cwd 是使用者自己的專案，往上三層也碰不到。

結果是 watcher 靜靜退回 `DEFAULT_HUB_URL`（`127.0.0.1:8787`）：安裝全綠、
watcher 掛得起來、**指派掃描清單上就是看不到它**。看起來像「那個人沒掛
watcher」，其實是掛了但連錯地方。

修法照 `--kind` / `--label` 的先例——**顯式 > 檔案**：

- `watch.py` 新增 `--env-file`，等同設定 `CHATROOM_ENV_FILE`
- `main()` 的 parse 移到 `load_env_file()` **之前**（反過來的順序下那個旗標
  永遠來不及影響載入，而它不會報錯）
- `install.py` 產的指令一律帶上 `--env-file "<kit>/.env"`
- `site_packages()` 回 `None` 時不再靜默降級，並對最終腳本做一次 `is_file()`

> 已經裝出去的 kit 手上是舊的——**升級後要重跑一次 `install.py`**，或在既有的
> Monitor 指令裡自己補上 `--env-file`。

## 🔴 四處文案叫人去關一個不存在的視窗

09/11 起 Hub 與隧道都改成隱藏啟動（`_launchHidden`），但「關掉那個視窗也等於
停止」這類指示留在四個地方。照著做的人會在工作列上找一個永遠找不到的東西，
然後以為關不掉。

其中一處的防漏測試**寫了卻搆不到**：斷言找的是「關掉那個視窗」，實際字串是
「關掉那個**隧道**視窗」，子字串比對永遠為假，於是那條 `findsNothing` 恆綠。
已改成搆得到的比對，並補上正面斷言——只驗「找不到錯的」的守門，在整個區塊
沒渲染出來時也會綠。

順帶：主控台的「開隧道」按鈕原本在偵測到殘留 `.tunnel-url` 時一律顯示
「已經有一條」。現在依探測狀態分歧，`unknown` 改說「偵測到舊網址」並指出
打不通時先按「關閉隧道」清掉。**禁用邏輯刻意沒有放寬**——`unknown` 同時
涵蓋「活著但本機繞不回來」，而那正是開第二條會留下關不掉的公開入口的情況。

## 🔴 手冊指向一支不存在的工具

`chatroom_guide` 與 `chatroom_board` 的說明都叫 agent「走
`chatroom_board_task_assign` 的指派協定」——bridge 沒有這支工具。Hub 端點是
存在的，只是 bridge 沒開。已改成指出真正的出路（請原持有者 `release`，或請
房裡的人類用 App 指派）。

## 🟠 三個數字對不上實作

| 位置 | 原本寫 | 實際 |
|---|---|---|
| `chatroom_board` 說明 | `idle_timeout` 預設 30 分 | **10 分**（`CHATROOM_IDLE_TIMEOUT`） |
| 手冊 §9.5、README ×2、v1.2.2 釋出說明 | 封存滿 3 天清除 | **15 天**（09/06 改的，`CHATROOM_PURGE_ARCHIVED_DAYS`） |
| 手冊 §5 | `ask_human` 逾時「預設 3 分鐘」 | `timeout` 預設 **60 秒**；3 分鐘是 `question_ttl`，兩者是不同的東西 |

`idle_timeout` 那個往寬鬆方向錯三倍——agent 會以為自己有 30 分鐘的安靜額度。

## 🟠 手冊停在已被推翻的舊版

「認領與改卡只能用 `room_id`」這條封鎖 09/06 起就解除了（Hub 改認
`board_member`），而 `_item_axis` 的 docstring 當場記著「那句話 09/06 起不
成立」，只是沒人回頭改手冊。現在真正還在的限制只有一條：**帶 `subagent`
時必須用 `room_id`**。

## 🟠 App 文案對齊實際行為

- **封存不是只讀，是會被永久刪除。** 整套封存文案（橫幅、選單、toast、
  錯誤訊息）沒有一個字提到 Hub 會在封存滿一定天數後把房間連同訊息與附件
  刪掉，而畫面上還有「解除封存」，讀者必然推出可逆。天數**刻意不寫死**——
  Hub 沒有任何端點把它吐給 client，寫死在自架 Hub 上就是假的。
- **通知設定**：「所有訊息」配上「有新訊息時」，讀者會推出「開著就不會漏」。
  實際上自己發的、system 訊息、正在看的房都不通知，而且 app 關閉期間的訊息
  **不補發**。選「關閉」也仍然會在被 @ 時亮工作列徽章（刻意設計，但文案
  一個字都沒說）。
- **待補投**：沒說它會放棄（TTL 30 分、佇列上限 50），而且點名的主因與實際
  最常見的情況相反。
- **Codex 轉送**：只講了它做的四件事之一。
- **`@agents` 不會叫醒子代理**（Hub 展開時排除 `ephemeral`），但子代理在
  成員面板上看得見、會說話。
- **撤銷邀請**：REST 每次都查，但 WebSocket 只在握手驗一次——已連上的人會
  繼續即時收訊息直到連線自己斷掉。
- **踢人**：會把對方加入時用的邀請碼**整張撤銷**（與他共用同一張的人一起
  斷）；若他是用主 token 進來的則什麼都撤不掉。
- **邀請人類的空狀態**把授權界線講成事實——那份清單只列得出與你用同一張
  邀請碼連進來的人。
- **搬卡**：「收回這裡」拿不回來，目標階段上那張新卡不會跟著消失。
- **板封存橫幅**講錯了是誰被封存（觸發它的是板的狀態，不是房間的）。
- **`API token 是空的 ⇒ 每次請求被拒`** 在開放模式下不成立（Hub 沒設 token
  就是完全開放，本機／測試 Hub 是既有用法）。
- 另修：釘選其實會發系統訊息並通知原發話者、刪房不會刪掉板上的卡、
  想法板的 agent 權限、掛板的另兩道閘、指派命名的 32 字上限、
  以及 11 處會原樣印給使用者的 `**` 星號。

## 已知待辦（這一版**沒有**處理）

- `chatroom_board_update` 的白名單放行 `complete`，而那一步只有人類按得下去
  ——agent 送過去會穿過 bridge、被 Hub 以 403 擋回。這一版只改了說明，
  白名單本身待裁。
- App 收到踢人回應裡的 `access_still_open` 卻沒用它。server 特地回這個欄位
  就是為了不讓管理員誤以為踢出等於切斷存取，目前靠靜態文案代替。
- 主持人模式的 `warn` 沒傳給 ROOMS 分頁，「伺服器沒有照做」在那裡顯示不出來。
- 邀請人類失敗時，Hub 回的錯誤字串是「這個 agent 不屬於你」——邀請一個
  「人」卻被這樣告知。
- 封存天數沒有任何端點吐給 client。要在 App 顯示真實天數得先補端點。
- 已打包的 `dist/` 產物仍帶著舊敘述，下次 build 才會同步。
